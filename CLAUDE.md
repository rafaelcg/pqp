# CLAUDE.md — agent guidance for pqp

Open-source Discord-like voice + text chat (**pqp.gg**). Repo: [rafaelcg/pqp](https://github.com/rafaelcg/pqp).

For current product status and open work, see [`docs/HANDOVER.md`](./docs/HANDOVER.md). Deeper design: [`ARCHITECTURE.md`](./ARCHITECTURE.md). Deploy: [`docs/DEPLOY.md`](./docs/DEPLOY.md), [`docs/deploy-fly.md`](./docs/deploy-fly.md).

## Stack

- **Monorepo:** pnpm workspaces (`pnpm-workspace.yaml`)
- **Client:** React 19 + Vite + Tailwind + Clerk (`@clerk/clerk-react`)
- **Server:** Node HTTP API + WebSocket (`/ws`) + Postgres
- **Shared:** Zod schemas / protocol types (`@pqp/shared`)
- **Desktop:** Electron shell (loads web client)
- **Auth:** Clerk JWT (Bearer on HTTP; first WS message `{ type: "auth", token }`)
- **Voice:** the server picks the media path per room and pins it: peer-to-peer WebRTC for DM calls and small servers, a LiveKit SFU for communities and servers of ten or more (live on `pqp-api`). Signaling and presence stay on the same WS in both

## How to run (local)

```bash
pnpm install
cp .env.example .env
cp .env.example client/.env
# Fill Clerk keys, or enable DEV_AUTH_BYPASS (see below)

docker compose up -d postgres
pnpm dev
# Client http://localhost:5173 — Server http://localhost:3001 — WS /ws

# Optional MinIO for file attachments (creates the bucket too)
docker compose --profile storage up -d postgres minio minio-init

# Optional desktop shell (Vite must be up)
pnpm electron:dev
```

**Dev auth bypass** (no Clerk): set `DEV_AUTH_BYPASS=true` in root `.env` and `VITE_DEV_AUTH_BYPASS=true` in `client/.env`, then restart server.

With the bypass on, API boot seeds a **Sandbox** hall (text + voice, dummy members, a few messages, one bot). Opt out with `DEV_SEED=false`. Vitest suites truncate: set `TEST_DATABASE_URL` to a copy (`pqp_test`), never to `DATABASE_URL`.

**A second local user** (voice, watch party, DMs, friends, reactions — anything that needs two people). The bypass signs *every* browser in as one shared "Dev User", so two windows are the same account and a two-person feature looks broken rather than untested. To get a genuinely separate account, set a suffix in the second window's console **before** loading `/app`:

```js
localStorage.setItem("pqp:dev-user-suffix", "bob")  // then reload
```

That window becomes `dev_user_bob`, a real row in the database with its own onboarding, presence and seat in a voice room. The first window is untouched. Any `[a-z0-9_-]{1,32}` suffix works, so `alice` / `bob` / `carol` give you three. The server half is `devBypassIdentity` in `server/src/auth/clerk.ts`; the client half is `devAuthToken` in `client/src/lib/dev-auth.ts`.

Same-machine testing needs no second browser profile and no private window, because the suffix lives in `localStorage`, which is per-origin *and* per-profile — but two normal tabs on the same profile share it, so set the suffix in one and **only** one.

## Architecture (short)

```
Browser/Electron → Clerk (auth)
                 → HTTPS API (servers, channels, messages, /api/ice-servers)
                 → WSS /ws (chat + presence + WebRTC offer/answer/ICE relay)
                 → P2P mesh (audio); TURN when cross-NAT
                 → S3/R2 direct (attachment bytes, presigned; never via the API)
```

- **Transport per room:** mesh caps at `MESH_VOICE_LIMIT` (8) and is what DM calls and servers under `LARGE_SERVER_MEMBER_THRESHOLD` (10) get; listed communities and larger servers go to LiveKit automatically (`server/src/voice/transport-policy.ts`), which is **configured on `pqp-api` today** (`/ready` reports it). **LiveKit SFU is implemented** — set `LIVEKIT_URL` / `LIVEKIT_API_KEY` / `LIVEKIT_API_SECRET` and the server advertises it via `GET /api/voice/backend` (no client rebuild). Presence stays on `/ws` in both modes; only media moves. A room's transport is decided by the server, pinned for the room's lifetime and stated in `welcome` — a client that cannot use it is refused rather than silently split off from the call. `cloudflare-sfu` is still a stub that falls back to mesh. See [`docs/voice-backends.md`](./docs/voice-backends.md).
- **Attachments:** S3-compatible storage (R2 hosted, MinIO local). The API only signs URLs — the browser PUTs and GETs the bytes itself. Off entirely unless `S3_*` is configured. Size is enforced twice: `Content-Length` is signed into the presigned PUT (verified against MinIO, not yet against R2), and the claim `HEAD`s the object — which is also what catches "never uploaded" and a stored type that differs from the signed one. That HEAD runs *before* the claim transaction opens; nothing between `BEGIN` and `COMMIT` may touch the network. See [`docs/ATTACHMENTS.md`](./docs/ATTACHMENTS.md).
- **Watch party availability is data, not configuration.** `servers.live_hls_enabled` is a tri-state column read per request: TRUE is on, FALSE is off *even when the environment says yes*, NULL falls back to `LIVE_HLS_SERVER_ALLOWLIST` exactly as before. `LIVE_HLS_ENABLED` is still the master switch above all three. The operator flips it from the dashboard with no deploy and no restart; a self-host with no dashboard keeps the environment variable it always had. `resolveLiveHlsForServer` in `server/src/voice/hls-egress.ts`, and `docs/WATCH_PARTY.md` §"Widening it is a click now".
- **Communities:** a public directory of joinable servers, entirely behind `COMMUNITIES_ENABLED` (default off, exposed to the client via `GET /api/communities/config` like the attachments/GIF configs). A community is a `servers` row with two switches: `is_community` is the **public address** (`pqp.gg/c/<slug>` answers, whoever holds the link joins with one tap, Manage Server may set it) and `is_community_listed` is the **directory** (browsable and searchable by any account, owner-only, requires an address). Every directory read runs auth and hides servers the viewer is banned from; joining reuses `redeemInvite`'s semantics without an invite row. Reports about a community go to the **instance** queue, never to that community's own owner, and the operator can unlist one with a single `UPDATE servers SET is_community_suspended = TRUE`. See [`docs/CONTENT_SAFETY.md`](./docs/CONTENT_SAFETY.md) §Communities — turning it on moves the instance out of Brazil's private-messaging liability exemption (STF, Art. 19, 26 Jun 2025).
- **Handles:** `users.handle` is a *second*, genuinely unique name (`username` is only unique paired with `discriminator`), claimed first-come, NULL for most accounts, one rename per 30 days. It addresses `pqp.gg/@rafa` — the public profile page, served by the unauthenticated endpoint that answers with a person: display name, avatar, an optional uploaded banner (`users.banner_key/banner_url`, on the avatar machinery), public-community badges, **opt-in** Steam / Battle.net / Twitch connections (`visibility = public`), the newest six **approved** depoimentos, and a join month. No id, no tag, no email, no presence. ## Pitfalls already hit

1. **Cross-NAT voice FAILED** — STUN-only is not enough; dead Open Relay creds were unreliable. **Fixed (2026-07-11):** Railway `TURN_*` (ExpressTURN) via `/api/ice-servers`, plus client Retry / ICE restart. Retest: hard-refresh both clients and rejoin voice.
2. **Clerk `getToken` remount loop** — unstable token getter in React deps caused remount storms; keep token access stable (ref / memoized callback), don’t put a fresh `getToken` identity in effect deps every render.
3. **Pages without API URLs** — empty `VITE_API_URL` / `VITE_WS_URL` makes `/app` hit same-origin Pages (no API). Set GH secrets and redeploy web.
4. **Clerk origins** — allow Pages + API origins in the Clerk dashboard.
5. **`@pqp/shared` on Railway** — production resolution needed a dedicated fix; rebuild/shared packaging matters for Docker deploys.
6. **pnpm version** — CI uses pnpm matching the lockfile (pnpm 10); don’t downgrade casually.
7. **Electron Linux artifacts** — scoped package name broke `.deb` paths; fixed in CI metadata.
8. **`curl` against `/api/...` returns 401** — there is no public-route allowlist; `handleApi` resolves a Bearer token before the router runs, so even `/api/attachments/config` and `/api/gifs/config` need one. Locally: `-H "Authorization: Bearer dev-local-token"` with `DEV_AUTH_BYPASS=true` (the bypass is ignored when `NODE_ENV=production`). The exceptions, all handled *before* that resolution and none of them router routes: `/health` (Fly's check and the Vultr box's Docker healthcheck — **process liveness only** as of A3.1 of `docs/plans/ALWAYS_ON.md`: draining, and that this HTTP server is listening, nothing that touches Postgres. Used to run `SELECT 1`; on 2026-09-12 that coupling was the incident — Postgres collapsed, the pool saturated, `/health` failed with it, and the platform stopped routing to the only machine, taking WebSockets, the HLS playlist proxy and every cached read down too, none of which needed Postgres at that instant. A DB-dependent route now answers its own fast 503 instead, via the circuit breaker in `server/src/db.ts` — see the pitfall below), `/ready` (the deep check for external monitors: Postgres, pool, LiveKit, storage; 503 when any is not ok; see `docs/MONITORING.md`. Because `/health` no longer proves a broken release can reach Postgres, `deploy-api-fly.yml`'s post-deploy verification curls `/ready` too, so routing health and deploy safety are two different checks), `/up`, `/status.json`, the embed-image proxy, `/api/avatars/:userId`, `/api/users/:userId/banner`, webhook execution, `GET /api/public/profiles/:handle`, and `GET /api/public/communities/:slug` (the last also behind `COMMUNITIES_ENABLED`, and 404 when it is off).
9. **Cloudflare TURN was configured, deployed and never once used**. `getIceServers` returned on the first match and static `TURN_*` was first, so the Cloudflare credentials sitting on the API were dead code, and a static relay that was throttled or down took cross-network voice with it because nothing else was ever consulted. Compounding it, the Cloudflare response parser required `iceServers` to be an **array** and tested `.length`, but Cloudflare answers with a single object, so even when it was reached it returned null. Two silent failures that looked identical to "working, on the other provider". **Fixed (2026-08-26):** order is now Cloudflare, then Metered, then static as the fallback; the parser accepts either shape; `TURN_PREFER_STATIC=true` restores the old order in one command without a deploy. Pinned by `server/src/services/ice.test.ts`, which asserts *which* relay comes back rather than that the list is well formed.
10. **Persistent "Realtime connection closed" on hosted deploy** — no WS heartbeat/reconnect, plus any thrown WS handler error crashed the whole server (unhandled rejection → Railway restart → every client dropped). **Fixed (2026-07-11):** server ping/pong heartbeat + try/catch around WS handlers + `pool.on("error")`; client auto-reconnect with backoff that resolves a fresh Clerk token per attempt (`client/src/lib/realtime.ts`).
11. **Merging to `main` restarts the API.** A server or `packages/shared` change is `restarts-api`. Since the 17 September 2026 cutover, production is the Vultr box (`deploy-api-vultr.yml`, `tools/api-host/`): two API containers, `api-a` and `api-b`, behind Caddy, sharing chat fan-out and the voice peer map through Postgres (`CLUSTER_BUS` / `VOICE_REGISTRY`, both on). `pqp-deploy.sh` recreates them one at a time (`api-a` confirmed healthy on the new tag, only then `api-b`), so one container is always serving and a redeploy no longer closes every `/ws` at once; a socket on the container being recycled reconnects onto its sibling. Losing the whole box is still full downtime, and the Fly path (`deploy-api-fly.yml`, one machine) is now the dormant rollback target with its apps at zero machines. On the container that is recycled, that machine drains rather than drops: `/health` goes 503 first so the proxy stops routing to it, then the sockets get 1001 in batches of 50 every 100 to 150 ms (`server/src/lib/drain.ts`), and with two machines (`docs/deploy-fly.md` 6a-bis) the reconnects land on the one that stayed up. After #162, refreshed **web and Electron** keep the media session and resume the same peer id (90s orphan window in-process; HMAC token lasts hours so a long call still reconstructs after a Fly restart). **iOS in a LiveKit room** keeps its media across the restart the same way (it declares `resume` and presents the token). **iOS in a mesh room, Android**, failed resume, and tabs that have not refreshed still drop out of voice. Client-only Pages deploys do not restart the API. This is the usual case. It is not a hangup. Apply `drops-voice` only when the change itself will hang up a live call even after resume. An API restart alone does not earn that label. Say `restarts-api` in the PR when it applies, before claiming the PR is safe to merge. Provider keys (Steam, Twitch, Battle.net) live on Fly, not in git; merging connection code without those secrets must not 500 production.
12. **Roster deltas were deployed and never once sent in production.** `sendRoster` had `registryOn() ? null : foldRoomEvents(events)`, production runs with `VOICE_REGISTRY=postgres`, and every delta test ran with it off. `voice.roster.deltas` read 0 for days and was blamed on browsers that had not reloaded. Same shape as pitfall 9: the flag that changes the code path was not the flag the tests exercised. **Fixed (2026-09-07):** with the registry on the delta is a diff of the rows against what the process last sent (`diffSentRoster`), pinned on a real Postgres by `server/src/ws/voice-roster-delta-registry.test.ts`. When a feature is gated by a flag that production sets, test it with the flag set, and read the counter that proves it runs.
13. **Voice seats outlived the people in them, for fifteen hours.** Ten of nineteen live rooms held exactly one person on 2026-09-08, `orphaned_at` NULL, and the process agreed the sockets were alive. The seat that started it was released correctly (`voice.leave`, `roomSize=0`, id retired) and then **re-inserted six milliseconds later** by the `set-voice-state` frame the client had sent just before hanging up. `trackRowWrite` claimed to order a channel's writes but joined them with `Promise.all`, so both statements were already in flight on two pooled connections and Postgres ran the DELETE first and the UPSERT second. The resurrected row carries a **live** `instance_id`, and `reconcileVoiceRegistry` refuses by design to touch a row whose owner is answering its heartbeat, while the owner has no peer left to release it: immortal, and on every roster. **Fixed (2026-09-08):** `trackRowWrite` takes a thunk and starts the write inside the chain, keyed **per peer** so a room's other seats and their hangups never queue behind one slow statement (completion stays per channel, which is what the roster reads wait on); `writePeerRow` refuses to write a peer the map no longer holds; and `sweepOwnStaleVoicePeers` reclaims, every 15s on the instance heartbeat, any row this instance owns that its map does not, with a 60s grace and `orphaned_at IS NULL`. That last clause is the definition, not an optimisation: a ghost is a row the close path never stamped, while an orphan is a seat deliberately held for the 90s resume window, and the two windows overlap. Narrowing the chain also made an old documented race reachable, so `deleteVoicePeer` is now two statements instead of one CTE on one snapshot, and two simultaneous last-leaves clear the room row instead of each seeing the other still seated. `voice.seats` on `GET /api/admin/metrics` reports idle seats, the oldest, and both counters. Two lessons, both already on this list: a fire-and-forget write is not an ordered write, and every sweep needs a case for **its own** rows. A related half came from the iOS audit (#411): `join-voice-room.resume` is a self-report, its schema says in as many words that phones omit it, and an iOS build sent it for every room anyway because it read `GET /api/voice/backend`, which answers what a *new* room on this deployment would be pinned to rather than what *this* room is. Production runs LiveKit, so it said yes to mesh rooms too, and that build tears its peer connections down on reconnect. Every conversation call is mesh by policy, so **every DM call from an iPhone left a phantom participant for 90 seconds**. The server cannot catch a build that lies about itself: it knows the room's transport exactly and has no signal at all for whether a client can rebuild mesh media, and guessing from a fingerprint (which caps a build happens to send, its user agent) is pitfall 12 waiting to happen. So the fix is a narrower promise the client has to opt into, `mesh-resume`, with `VOICE_MESH_RESUME_REQUIRES_CAP` treating a client that never makes it as unable. That reaches every build already on a phone without an app update, and it is off until browsers have cycled onto the bundle that declares it. Beside it, a second finding of the pitfall-9 shape: `startHeartbeat` in `server/src/ws/index.ts`, its two-strike rule and the whole of `heartbeat.test.ts` were **dead code**: `server/src/index.ts` ran its own inline one-strike copy. There is one reaper now, and `heartbeat.test.ts` reads the entry point to keep it that way.
14. **The web client published every microphone with no source, and a watch party's audience could not be heard at all.** Sampling a live production party on 2026-09-09 showed the host's microphone as `source: 0` (`SOURCE_UNKNOWN`) beside a screen share correctly tagged `3`. `new LocalAudioTrack(raw)` starts at `Track.Source.Unknown` and `publishTrack` only overwrites that when a `source` is passed; the client passed one for the camera and for both halves of a screen share, and not for the mic. Android's publish carries a comment saying it copies "both halves of what the web client publishes", about the two halves it did copy. **This was not cosmetic.** `liveKitPublishGrant` sends `canPublishSources: ["microphone"]` to anybody holding SPEAK and not STREAM, and LiveKit treats a non-empty list as an allowlist that UNKNOWN is not in (`VideoGrant.GetCanPublishSource`, livekit/protocol). In a `watch_party` channel the stream bit is START_WATCH_PARTY, which no ordinary member holds, so **exactly that grant is what an invited speaker gets**: the media server refused their microphone while their own app showed them live and unmuted. Nothing on either side could see it, because the server's own moderation reads `type === AUDIO` and works on an untagged track, so every test and every audit of the mute path passed. Two lessons. A grant written against an enum is a contract with the client, and nothing checks that the client keeps it: the load harness at `tools/watch-party-load` set the source correctly, so the rig was more correct than the product. And when a picker or a grant keys on a field, assert the field on the **publish** side too, which is what `client/src/lib/livekit-session-sources.test.ts` now does for all three sources. **Fixed (2026-09-09):** client-only, so tabs that have not reloaded keep the old behaviour until they do.
15. **A watch party's transcode leaked handlers onto the media box, and a stalling stream was the only symptom.** The same live party logged two `voice.hlsStarted` for one channel nine minutes apart, same presenter, **with nothing at all logged in between**, and the first pair's egress handlers were still running two minutes after the second pair started. Two causes, both of the usual shape. `rungHealth` returns "ended" for two different reasons and only one of them means the handler is over: LiveKit saying so is final, while "the playlist has not moved for 20 s" is a rule that exists precisely *because* a killed egress node is reported ACTIVE forever, and its mirror case, a handler still transcoding while its output stalled, was dropped from `rooms` and **never stopped**, then had a fresh ladder started beside it by `scheduleRestart`. And three of `stopRoom`'s five callers logged nothing, while `pushLiveHls` resolved the channel's server id only when it had a sharer and passed `null` otherwise, so an ordinary end of share was torn down by the not-allowlisted branch (silent) instead of the no-share branch (which logs). **Fixed (2026-09-09):** `stillRunning` tells the two halves of "ended" apart and a stalled rung is stopped; every teardown carries a `reason`; and `reapForeignEgresses` stops, on every monitor tick, any ACTIVE egress in a room this process is presenting that is not one of its own rungs, counted by `liveHls.orphansStopped`, which belongs at zero. Scoped to rooms we hold a session for on purpose: "stop everything I do not recognise" would kill what `adoptLiveHlsSession` exists to inherit across a deploy. The lesson beyond the bug: **`LIVE_HLS_MAX_SESSIONS` counts sessions, and a cap only means what it says while a session is a fixed number of processes.**
16. **A dead Clerk JWT vetoed a valid capability token, and stalled every web viewer of every watch party.** The playlist proxy takes two credentials: a Bearer header, and a `?t=` capability this server signs itself, which names the user, the channel and the session and is minted only after a real access check. `handleApi` resolves a Bearer **before the router**, so any `Authorization` header had to succeed or the request was 401 before the token in the URL was ever looked at, and the token-only door was gated on `!req.headers.authorization`. `hls.js` attaches a Clerk JWT through `xhrSetup` **on top of** the `?t=` already in the URL, caches it in a closure and refreshes it every 30 s without `forceRefresh`, while a Clerk JWT lives about 60 s. So roughly once a minute every playlist request carried an expired token and was rejected: the player stalled, retried, recovered, and did it again a minute later, for the whole film. **Why nothing caught it**: every server test and every `curl` sent only `?t=`, which is the one request shape that never fails, and native iOS and Safari send only `?t=` too. There was even a test named "serves hls.js (header AND token)" and it used a VALID header, so it exercised the shape and not the failure inside it. The failure existed solely in the combination a browser produces. **And the proxy logged nothing on a 401**, so from the server every measurement said the stream was healthy; it took a screenshot of Rafael's network panel after an afternoon of looking. **Fixed (2026-09-09):** the capability is tried again after the Bearer resolution FAILS, which is late enough that there is no other caller to confuse it with (trying it first would let a token serve a caller whose header resolves to somebody else, a rule this route already had and keeps); the client stops attaching a header when the URL already carries a token; and `voice.hlsPlaylistRejected` says which of missing, malformed, bad-signature, expired, wrong-channel, wrong-session it was, rate limited per channel per reason. Three lessons: **a second credential is a second thing that can fail**, and "belt and braces" is only true if neither strap can veto the other; a test that sends one request shape proves nothing about the shape the product sends; and an endpoint that refuses somebody must say why, or the next one of these costs an afternoon too.
17. **`/health` ran `SELECT 1`, so a Postgres collapse took down everything, not just the database.** On 2026-09-12 Postgres saturated the pool; `/health` opened its own fresh connection for the check and failed along with it; Fly (and any load balancer routing on it) had nowhere healthy to send traffic and stopped routing to the only machine — dropping every WebSocket, the HLS playlist proxy and every cached read, none of which touch Postgres to do their job. The health check the proxy routes on had become a proxy for "is the database up", which is a different question from "should traffic keep reaching this process". **Fixed (A3.1, 2026-09-13):** `/health` is process liveness only (draining, HTTP server listening) — database health moved entirely to `/ready`, which was already built for exactly this and was never on `fly.toml` or the Docker healthcheck. A small circuit breaker in `server/src/db.ts` (`createDbBreaker`, `server/src/lib/db-breaker.ts`) watches pool queue depth and its own `SELECT 1` probe — on a dedicated connection, never the shared pool, so a stalled query cannot itself consume the capacity the breaker exists to protect — with hysteresis (needs `DB_BREAKER_GRACE_MS` of sustained badness to open, `DB_BREAKER_HALF_OPEN_SUCCESSES` consecutive good trials to close). While `open` **or `half-open`**, every `pool.query`, `pool.connect()` and the `PoolClient.query` of whatever `connect()` returned (transactions included — a first review of this change caught that only `pool.query` was wrapped at first, leaving every `BEGIN`/`COMMIT` write in the codebase able to hang the pool anyway, and that `half-open` let ordinary traffic through instead of admitting only the breaker's own recovery trial) fast-rejects with `DatabaseUnavailableError` instead of queueing for `connectionTimeoutMillis`, and the few chokepoints that funnel almost every DB-dependent HTTP route (`handleApi`'s central catch, the admin machine-route catch, the HLS token doors in `server/src/api/index.ts`) turn that into a 503 with `Retry-After: 5` and `{ error: "database_unavailable" }` in milliseconds. The HLS playlist proxy and its master-playlist rung list keep answering from the last body they rendered while the breaker is open, falling back only on that specific error, only for up to `STALE_ON_BREAKER_MAX_MS` (30s) past the last render that actually confirmed the session live — long enough to ride out the breaker's own recovery cycle, short enough that a session which legitimately ended right as the breaker opened for an unrelated reason cannot go on being served for the rest of a long outage. A chat send that hits the breaker before `createMessage` commits gets `message-rejected` with reason `database-unavailable` (retriable, unlike `no-access` or `automod`) instead of a silent drop that only resolves as a generic failure after the client's 10s timer; a failure in a *post*-creation step (recording mentions, the thread-chip update) still propagates as a real error rather than telling an already-successful sender to retry into a duplicate post. `DB_BREAKER=off` is the rollback switch; `db.breaker.state` / `.opened` / `.rejected` are on `GET /api/admin/metrics` under `runtime.db.breaker`, sampled live even when the cached half of that same payload is itself serving a stale snapshot because the breaker is open. The lesson: **the health check a proxy routes on must fail only for reasons that make routing away correct** — anything a request doesn't actually need should not be able to veto it. A related lesson from getting the breaker itself reviewed: **a circuit breaker that only wraps the entry point everyone remembers (`query`) is not a circuit breaker for the paths that go around it (`connect()`, a "trial" state that quietly admits everyone) — enumerate every door before trusting the one you built for.**
