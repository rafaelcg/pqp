# Mobile / PWA

pqp installs to a phone home screen as a standalone app. There is no separate
mobile codebase — it is the same SPA, plus a manifest, a service worker, and the
handful of things a browser tab gets for free but an installed app does not.

Built last on purpose: its scope had to reflect the whole feature surface rather
than guess at it.

## What it does

| Piece | Where |
|---|---|
| Manifest (name, icons, `start_url: /app`, standalone) | generated by `vite-plugin-pwa`, configured in `client/vite.config.ts` |
| Service worker (shell precache + SPA fallback) | generated, `registerType: "prompt"` |
| Update prompt UI | `client/src/components/layout/update-prompt.tsx` |
| Registration wrapper | `client/src/lib/register-sw.ts` |
| Notification click handling | `client/public/sw-notification-click.js` |
| Icons + generator | `client/public/icons/`, `scripts/generate-icons.py` |
| Cache headers | `client/public/_headers` |

## Decisions worth knowing

**The page is never reloaded at a bad moment, and never left behind.** The client
holds a live WebSocket, unsent composer drafts, and possibly an active call.
Swapping the bundle out from under any of those is worse than running the
previous build for another minute, so the reload happens at a safe moment or when
the person asks. What stands behind that, and why a window can no longer stay on
an old bundle, is the next section.

**Only the shell is cached.** Messages, avatars, and uploads are never
precached — a chat app serving yesterday's messages out of a cache is worse than
one that admits it is offline. In production the API is a different origin
anyway, so there is nothing app-shaped for the worker to catch by accident.

**`navigateFallbackDenylist` matters more than it looks.** Without it a request
to `/api/...` or `/status.json` that missed would be answered with `index.html`
and a 200, and the client would try to `JSON.parse` an HTML document. Verified
offline: an API request correctly fails with a network error instead.

**`/sw.js` and the manifest are served `no-cache`** (`client/public/_headers`).
A stale `sw.js` is the one file that can pin a user to an old build forever: the
browser only learns a new worker exists by re-fetching that exact URL.

**Notifications go through the worker on Android.** Chrome there refuses
`new Notification()` outright and only raises notifications from a service
worker, so `deliver()` in `client/src/lib/notifications.ts` falls through to
`showNotification`. Those clicks arrive in the worker rather than the page,
which is what `sw-notification-click.js` is for — it focuses an existing window
where possible rather than opening a second copy of the app.

**iOS needs its own meta tags.** It ignores the manifest for the status bar and
the home-screen title, so `apple-mobile-web-app-*` are set in `index.html`
alongside it. `black-translucent` lets the app draw under the status bar, which
is only safe because the viewport is `viewport-fit=cover` *and* the shell insets
itself — see the `@media (display-mode: standalone)` block in
`client/src/index.css`. The insets are standalone-only; applying them in a
browser tab leaves a dead band under the existing chrome.

**Heights use `dvh`.** On mobile Safari `100%` resolves against a viewport that
includes the URL bar, so the composer sits below the fold until the bar
collapses. Applied via `@supports` on top of the existing `100%`, so a browser
without `dvh` keeps the old behaviour rather than losing its height entirely.

**Dialogs use `visualViewport`, because `dvh` is not enough for them.** `dvh`
tracks the URL bar and nothing else: neither the on-screen keyboard nor a zoom
changes it, and both change what the user can see. A `position: fixed` overlay
sized to the layout viewport is then bigger than the screen — with the keyboard
up its footer is underneath the keys, and under Safari's focus magnification
(which fires on any focused field whose text is smaller than 16px) it is wider
than the display and loses its own left edge off-screen. `client/src/components/
ui/dialog.tsx` positions the dialog layer from `window.visualViewport` instead,
falling back to `inset-0` where the API is missing, and the stylesheet holds
fields inside a dialog at 16px so the magnification has no reason to fire.
Geometry is asserted in `client/e2e/dialog-mobile-layout.spec.ts` at 320px and
390px — "the dialog opened" was true throughout the bug that motivated it.

## The home page's first load

`pqp.gg/` is a static SPA, and its first screen used to be empty until the JS bundle ran: on a mid-range phone over a slow link that was four to six seconds of dark background, and mobile Lighthouse scored it 64 (LCP 11.3 s). A prerendered first screen took that score to 90 and above (the PR that introduced it has the before and after table). That score was measured on the home page before the October 2026 redesign. The redesigned page uses the same mechanism. What changed, and the rules that keep it working:

- **The first screen is HTML** (`client/src/lib/prerender-hero.ts`, written into `index.html` by the `pqp-prerender-hero` plugin in `vite.config.ts`, build only). It holds the skip link, the header and the hero, in all three languages. The header has the logo, the BETA mark, the section links, the language picker, sign in and create. The hero has the sky picture, the headline, the body, the two buttons, the free line, a gap where the download line goes, the product frame with its picture, and the caption. It uses the same Tailwind classes as the React page. `<html lang>` picks which language shows. The edge middleware writes it, or the head script does on `?lang=`, a saved choice or the browser's languages. Every other route hides the block before the first paint (`data-route`). The buttons are links until React takes over: sign in goes to `/app`, and the two calls to action go to the intent links the live buttons use (`/app?create=new`, `/app?import=discord`). The height of the gap for the download line follows `data-plat`, which the head script sets to `ios`, `android` or `mac` (a Mac outside the desktop app). Other devices get no `data-plat`. **When the markup of `Nav` or `Hero` in `pages/home/index.tsx`, or a value in `pages/home/hero-media.ts`, changes shape, mirror it in `prerender-hero.ts`.** The words follow the catalogues on their own. `prerender-hero-parity.test.tsx` renders the live hero in all three languages and ten viewport modes, and fails on any difference.
- **React replaces it, nothing is hydrated.** `main.tsx` renders into `#root`, which clears the static block. On the home page only, that first render waits for the page to settle (`lib/boot-gate.ts`: load and idle, or a touch, a click, a key press or a wheel turn, or a 4 s ceiling). Then it fetches the language catalogue, resolves the download plan, loads the home page chunk, and waits for the static pictures in the first viewport to be drawn. The swap shows no English flash, no jump and no missing picture. `data-pre` on `<html>` switches the `animate-rise` entrance off, so the live copy does not fade in a second time. The static block draws the exact boxes of the live hero. On a production build, the headline, the sky, the frame and the caption moved by 0 px in the swap, in all three languages, at 1440 px and 390 px wide, and the swap added no layout shift. The static sky is the only largest contentful paint candidate. The live copy of a picture must never be strictly larger than its static twin, or the LCP would depend on the bundle (`THE LCP RULE` in `prerender-hero.ts`). At 1280 px and wider, the live header adds the Communities link and the status pill about one API round trip after the swap. They sit at the end of the row, so no other item moves, and the shift is at most 0.0011. The static block cannot draw them, because a self-host answers differently. A visitor who is signed in sees the sign-in link go and the create button turn into an open-the-app button once Clerk loads, for the same reason.
- **The app bundle starts after the first screen has settled**, not with the head (`lib/defer-entry.ts`, plugin `pqp-defer-entry`; the snippet is `lib/first-screen-gate.ts`). On every route but the home page it is fetched at once, as before. The analytics and advertising tags follow the same rule (`lib/deferred-tag.ts`). Hosted-only stays hosted-only: a build without the ids emits nothing, and no consent behaviour changed.
- **Fonts are self-hosted** (`client/src/fonts.css`, files in `client/src/assets/fonts/`): the exact Google woff2 subsets, metric-matched local fallbacks so the swap barely moves text, and only Gabarito and Instrument Sans (Latin) are preloaded. Do not reintroduce the remote stylesheet. The cookie and privacy pages still list Google Fonts among the third parties a page contacts; that text is legal copy with translation fingerprints and was not touched.
- **The hero pictures are two `<picture>` elements, not a CSS background.** The sky is a painted rooftop (`public/images/hero/`): AVIF and WebP at 800, 1200 and 1536 px wide. The frame holds the first frame of the `call-join` footage (`public/media/home/`) as a WebP: the 1920 px file (with a 960 px candidate in its `srcset`) on a window 1024 px wide or more, and the 960 px file below that or under Save-Data. With reduced motion the frame shows the six-person room still instead. The footage itself (MP4 and WebM) plays only once `manifest.json` in that folder lists it. It plays only while the frame is on screen and the tab is visible, and `preload` stays `none` until the frame is within 400 px of the viewport (`pages/home/cinema/clip.tsx`). `pages/home/hero-media.ts` holds these values, and `prerender-hero.ts` keeps a copy of them. The parity test fails when the two differ. The static `<picture>` picks the same file as the live `<img>` in each of its four states, so the second request is a cache hit. Save-Data is the one exception: no media query can read it, so the static block picks by width only. At 1024 px and wider, a Save-Data visitor can get the 1920 px file first and then the 960 px file after the swap, which is one extra download. The old CSS background (`.hero-bg-art`) and the hero background video (`lib/hero-video.ts`, `hero-background.tsx`) are gone.
- **The service worker is not installed by a reader.** Installing it precaches the whole shell (about 6.5 MB), so on the home page, for somebody with no worker yet, registration waits for a touch, a click, a key press or 20 s (`lib/register-sw.ts`). Everywhere else, and for anybody who already has a worker, nothing changed. This does not interact badly with "Nobody stays on an old bundle" below: a visitor with no worker has no stale precache to be pinned to, the build watcher and the forced-update screen mount with the rest of the app on the landing page and poll `/version.json` whether or not a worker exists, and `apply-update.ts` already copes with there being no registration. The Vietnamese, Cyrillic and Greek font subsets are left out of the precache.
- **Cache headers** (`public/_headers`): `/images/*`, `/media/*` and `/icons/*` are a day fresh plus a week of stale-while-revalidate; hashed `/assets/*` were already immutable. Rename a file rather than replacing it in place when it must change today.

## Nobody stays on an old bundle

Written after a field test on 2026-09-30: the desktop app (the Electron shell
loading `https://pqp.gg`) on one Windows 11 PC kept running an older copy of the
site after a deploy, with the new shell around it, so a share went out with no
sound. Reproduced with real builds and a real service worker (`client/e2e/stale-bundle/`).

**What kept a window on an old bundle, all of it true before this change:**

1. **A waiting worker never took over.** The build used `registerType: "prompt"`
   with no `skipWaiting`, so a new service worker installed and then WAITED for
   every window of the origin to close. Until it took over, the OLD worker's
   precache answered every navigation: in the repro, three reloads in a row came
   back on the previous bundle. An always-open desktop window never closes, and
   View > Reload does not help.
2. **Nothing looked for a new build.** The browser re-checks `sw.js` when the page
   navigates (and about once a day if the worker is asked to do something). A
   window that never navigates is told nothing for as long as it lives.
3. **The prompt was the only way out, and it gives way easily.** "Later" snoozed
   it, a call hid it, and it only appeared once something had noticed (point 2).
4. **No page knew which build it was.** There was nothing to compare with.
5. **Electron kept the old site across a shell update.** The service worker and the
   HTTP cache live in the profile, which a shell update leaves alone.
6. **The Cloudflare zone rewrites `sw.js`.** Checked on 2026-09-30: the Pages
   origin (`pqp-3yr.pages.dev/sw.js`) answers `no-cache`, as `_headers` says, and
   `pqp.gg/sw.js` answers `max-age=14400` with `cf-cache-status: EXPIRED`. The
   zone's Browser Cache TTL (4 hours) applies to cacheable extensions and beats
   the file. Browsers fetch the MAIN worker script past their cache, so this is
   latent for `sw.js` itself, but it is live for the script the worker imports.
   Files that are not on the zone's list (`.json`, `.webmanifest`, HTML) keep
   their headers, which is why the version file is JSON.

**What stands behind it now**, each piece a fallback for the one before:

| Piece | Where | What it does |
|---|---|---|
| Build id | `client/vite.config.ts`, `src/lib/build-info.ts` | The deployed commit (`VITE_FARO_APP_VERSION`, else `VITE_PQP_BUILD_ID`, else the local `HEAD`, else `dev`) is baked into the bundle and written to `/version.json` with the build time. A `dev` build never compares itself. `<html data-pqp-build>` shows it. |
| Worker takes over | `workbox.skipWaiting` + `clientsClaim` | A new worker activates as soon as it installs, so a reload reaches the new precache. The running page keeps the code it loaded; it is not reloaded by this. |
| Navigations are network-first | `src/lib/sw-build-script.ts` (imported by the worker as `sw-build-*.js`) | The worker answers a navigation from the network, and only falls back to the precached shell when offline or after 4 s. Before, every navigation was answered from the precache, which is the OLD build's until a newer worker has installed. A hard reload (Ctrl+Shift+R) bypasses the worker for ONE load, and the next navigation, the language picker's `location.replace` included, is the worker's again: reported on 2026-09-30 as "the old site came back after I changed the language". Reproduced with a second tab open (it keeps the old worker in control). The locale catalogues are hashed chunks of the same build, in the same precache, so they follow the build id like everything else, and an update reloads them with the page. |
| The page asks | `src/lib/version-watch.ts` | `/version.json` (no-store, cache-busted) on start, on focus and visibility, on every realtime (re)connect, and every 8 to 12 minutes whether the tab is visible or hidden, at most once a minute. Also asks the browser to look for a new worker. A worker taking control triggers a look at once. `/version.json` and not the API's version, because the bundle and the API deploy apart. |
| The worker asks too | `src/lib/sw-build-script.ts` | On a fetch from any page it controls, at most every 10 minutes (the time kept in Cache Storage, `pqp-sw-meta`), the worker calls `registration.update()`. This is what reaches a page whose own code never asks: see "Bundles from before any of this" below. |
| The daily announcement | `src/lib/client-version.ts` (`announceAtFor`), `version-watch.ts` | A build that is merely new is not told to an open page the minute it lands. It is announced at the next 09:00 UTC (06:00 in Brasília) after it has been live for an hour, so a page hears about at most one new build a day and a build replaced by a hotfix within the hour is never announced. The page still reads `/version.json` as often as before; it only holds the answer (`announceAt` in `update-prompt-state.ts`, plus a few minutes of per-page jitter so every window does not reload in the same second). Old bundles keep working meanwhile: the API stays backward compatible. `VITE_UPDATE_ANNOUNCE_HOUR_UTC` (0 to 23; `off` announces at once, for a self-host that wants the old behaviour). The operator skips the wait with `client_force_update` ("announce now") or a critical update. |
| The indicator | `update-indicator.tsx`, `server-rail.tsx`, `phone-screens.tsx`, `standalone-update-indicator.tsx` | A small round button with a dot, at the foot of the server rail (a phone: the header of the Servidores and "tu" screens, and a dot on the "tu" tab; a narrow window: a dot on the menu button; the landing page: a corner button). Click for a popover: "Nova versão pronta", when it was published, what changed (below), and **Atualizar**. It never opens by itself, blocks or reloads. With `client_force_update` on it is drawn filled with a pulsing dot (not under reduced motion). It replaced a corner card and a lime strip across a call. |
| In a call or a watch party | `update-indicator.tsx` | The popover says the update waits and installs on its own afterwards, and offers **Atualizar agora** behind a second question that names the cost (a reload ends the call and the screen share; a browser cannot restore a capture without the picker). |
| What changed | `scripts/build-changes.mjs`, `scripts/changes-lib.mjs`, `src/lib/update-changes.ts`, `deploy-web.yml` ("Write what changed") | The deploy writes `/changes.json` beside the build: the merged work that touched the web client since the build that is live, added to what was already listed (two weeks, so a window open for a week is told everything since ITS build). A change becomes a line in the popover only when its author wrote one for the person, as a line in a commit message (squash merges keep them): `Update note (pt-BR): Agora dá para arrastar os servidores na barra.` (also `(en)` and `(es)`; any subset). It is shown in the person's language or not at all; the rest are counted ("e mais 7 melhorias pequenas"), and a pull request title, which is written for a reviewer in English, is never quoted. The step never fails the deploy. The popover reads the file only when it is opened. |
| Safe moment | `src/lib/update-policy.ts`, `build-watcher.tsx` | Once a build is announced, reload with no question when the tab is hidden, right after a call ends (2 minutes), when nobody has touched the page for 3 minutes, or when it has been out of date past 12 hours counted from the announcement (`VITE_UPDATE_MAX_STALE_HOURS`, `0` turns it off). **Never in a call, never while sharing a screen (that is a call), never while watching a live party, never while typing on a visible tab (text in the focused field, or a key in the last 20 s), and ONE automatic reload per build, ever** (`sessionStorage`, no timer: it used to be one per 15 minutes). The call and watch-party check is asked again at the last moment, inside `applyUpdate`, after the worker has been brought up, because that takes up to 15 s and somebody may have joined a call in them; a reload refused there gives the build its one reload back. The stale-chunk recovery (`chunk-reload.ts`) asks the same question (call OR watch party). The only exception is a CRITICAL update, below. |
| Applying it | `src/lib/apply-update.ts` | Updates the worker, waits for it, asks the active worker which build it is (`sw-build-*.js`), and reloads. A worker that is not the target build, or does not answer, or does not take over in 15 s, gets its caches deleted before the reload, so the page loads from the network. The worker is never unregistered: a push subscription dies with the registration and can only be re-created from a click. |
| When applying fails | `src/lib/update-ladder.ts`, `src/hooks/use-apply-update.ts` | The indicator and the critical dialog take the update through a ladder, because a resolved `applyUpdate` proves nothing (it can reject, hang, or end by asking for a reload a browser refuses): after each rung it waits to see the page actually leave (`pagehide`). Rung 0 is `applyUpdate`; rung 1 deletes every cache and navigates to the same URL with a `?_pqp=` cache-buster (removed from the address again in `main.tsx`); rung 2, the last resort, also unregisters the workers (which drops the push subscription, so only for somebody who has failed twice). One click walks the rungs with a 1 s and 3 s backoff; if all fail the button comes back with the reason ("sem internet" or "não deu para atualizar", pt-BR, en, es) and the NEXT click starts on a heavier rung than the last one ended on (remembered in `sessionStorage` for 15 minutes). Offline is answered at once and touches nothing. Nothing reloads by itself in this path, so it cannot loop; the automatic path keeps its own guard. A button can never stay disabled past 120 s. |
| Operator levers | `forced-update-screen.tsx`, `server/src/lib/client-update-config.ts` | See below. |
| Electron | `electron/lib/web-cache.js` | Clears the HTTP cache and the worker once per shell version, and View > "Reload and clear cache" (Ctrl/Cmd+Shift+Alt+R) does it on demand. Sign-in and drafts are kept. |

**Pushing an update, and a critical one.** `GET /api/client-update/config`
answers `{ forceUpdate, minBuiltAt, interruptCalls, criticalMinBuiltAt }`, read per
request, all off by default. Since 2026-10-14 the first two only mean "announce now",
and only the last two block a screen:

- `forceUpdate`: the runtime flag `client_force_update` (dashboard, "interruptores",
  no deploy and no restart; `CLIENT_FORCE_UPDATE=true` is its environment default).
  **Announce now, with emphasis**: every client that is not on the latest build skips
  the daily wait, draws its indicator filled, and then follows the ordinary rules
  (reload at a safe moment, never over a call, a share or a watch party). It blocks
  nobody. Until 2026-10-14 it put up a blocking "Atualização necessária" screen for
  everybody on every deploy; it was ON from 2026-10-04 and a desktop user wrote, on
  2026-10-13, "de 10 em 10 segundos tem atualização". Turn it off once the rollout is
  done.
- `minBuiltAt`: `CLIENT_MIN_BUILT_AT`, an ISO date or epoch milliseconds. Bundles
  built before it are treated the same way (announce now). Self-limiting (a later
  deploy is built after it), but an environment variable, so it needs a recreate.
- `interruptCalls`: the runtime flag `client_force_update_in_call`. **Critical.** With
  either lever above forcing a bundle, that bundle reloads by itself even in a call
  (once per build) and a small blocking "Atualização necessária" dialog is up (one
  button, no Escape, no backdrop dismissal), which is what stays on screen if that
  reload does not land. It ends calls and screen shares: a critical fix only, off
  again after.
- `criticalMinBuiltAt`: `CLIENT_CRITICAL_MIN_BUILT_AT`, same format as
  `CLIENT_MIN_BUILT_AT`. Bundles built before it are critical: reload even in a call,
  and the dialog.

The last two are read by bundles from 2026-10-10 on; an older bundle ignores them
(and, until it updates once, still treats `forceUpdate` as the blocking screen it used
to be).

A force that was already known for a build is kept when a later lookup FAILS (offline, signed out, timeout); only an answer from the server, the operator turning it off included, changes it. A client asks only when it already knows it is stale, so an up-to-date client never
makes this request. The screen waits while the person is in a call and appears when
they hang up. It applies to a build that differs from `/version.json`, so a minimum
set past the newest build traps nobody in a reload loop.

**What a web deploy reaches.** The new logic ships in the bundle. A window that is
still on a bundle from before this change has none of it: it gets the new worker
(which activates on its own) on its next navigation or daily check, and the new
bundle on its next reload or relaunch, or when the old card is pressed (a bundle from before 2026-10-14 still has the card, the blocking force screen and the 20-minute snooze until it updates once). From that
load on, everything above applies.

**Bundles from before any of this** (built up to 2026-09-29) cannot run any of
the above, and the failed installs of 2026-09-30 to 2026-10-10 kept some of them
open. What still reaches them, all of it in code they already carry:

1. Their `virtual:pwa-register` (vite-plugin-pwa prompt mode, no `onNeedReload`)
   reloads the page when a worker it did not register takes control
   (`installed` with `isExternal`, then `controlling` with `isUpdate`). So once
   any update check finds a new worker more than a minute after the page loaded,
   the page reloads itself, **in a call too**: that is their code, not ours. Every
   bundle up to this change did it, the 2026-09-30 to 10-10 ones included; from
   this change on `register-sw.ts` passes `onNeedReload`, so the plugin never
   reloads and `update-policy.ts` decides (a call is never interrupted).
2. An update check happens on any navigation of the origin (another tab), on
   `registration.update()` from a newer tab of the same browser, from the worker
   itself once a current worker controls the page ("The worker asks too"), and
   from the browser after 24 hours.
3. Once a current worker controls the page, the old precache is gone, so the
   first lazy chunk the page asks for 404s and their `chunk-reload.ts` reloads
   (deferred with a banner in a call).
4. A page that loaded under the old worker in the same minute its update was
   found sees that update as its own, does not reload, and is current on its
   next navigation or at the next deploy (path 1).

The server has no lever of its own here: the WebSocket of those bundles has no
version or reload message, and a close only makes them reconnect.

**One thing to set by hand.** In the Cloudflare dashboard for `pqp.gg`, Caching >
Configuration > Browser Cache TTL: "Respect Existing Headers" (or a Cache Rule that
bypasses `/sw.js` and `/sw-notification-click.js`). Nothing in this repository can
set it. The client does not depend on it: the version file is read past every
cache, and an update whose worker turns out stale is delivered by purging.

### "De 10 em 10 segundos tem atualização" (2026-10-13)

A Windows desktop user (pt-BR, twelve days old) wrote, in capitals, that there was an
update every ten seconds and that "the screens stop and only the voice remains".
Three causes, one day (nineteen web deploys):

1. **`client_force_update` had been ON since 2026-10-04.** It meant "every client not
   on the latest build gets the blocking screen", so every deploy blocked every open
   window (a call only delayed it to the hangup). It now means "announce now, with
   emphasis" and blocks nobody; only a critical update blocks (above).
2. **Every deploy was announced to every window.** Nothing in the client had a notion
   of "not yet". A new build is now told once a day (`announceAtFor`), and an
   automatic reload is ONE per build, never in a call, a share or a watch party, and
   asked again at the last moment inside `applyUpdate`.
3. **"Only the voice remains" was a stale chunk in a call, not a reload.** Every
   deploy deletes the old hashed assets. A page that was open before it 404s on the
   first lazy chunk it has not fetched (the emoji and GIF pickers are the ones a
   person opens in a call chat). `recoverFromChunkLoadError` rightly refuses to
   reload a call, so it defers, and the only boundary above the lazy panel was the
   ROOT `ErrorBoundary`, whose "pqp updated, you are in a call" fallback replaces
   the whole app. The voice session lives outside React, so the audio carries on under
   a page with nothing on it. `error-boundary.test.tsx` reproduces it (the third
   test) and a contained boundary now costs the picker only
   (`ContainedChunkBoundary`). The recovery also treats a watch party like a call
   now.

   What was NOT found: an update reload or the blocking screen tearing down a share
   while the audio survived. In a call the policy never reloaded or blocked (except a
   CRITICAL update, which reloads a call by design: check that
   `client_force_update_in_call` is off, because with both flags on every deploy would
   have reloaded every call, and a web or desktop reload resumes the audio but cannot
   restore a screen capture). The Faro session of the report was not in Loki (sampled
   out); chunk errors do reach it (16 on 2026-10-09, Android Chrome).

The desktop shell had a fourth, smaller one: its own native "restart to update" box
came back every six hours for somebody who had said "Later", and could open over a
call (`electron/lib/update-prompt-policy.js`, `docs/DESKTOP.md` §5).

### A precache entry that 404s

Found on 2026-10-10. Symptom: a plain reload showed the old site and a hard
reload (Cmd+Shift+R) showed the new one, every time. Seen in Zen (Firefox) and
earlier on Windows.

Cause:

1. The worker precached every `**/*.html`, which included three standalone
   pages in `client/public/` (`share-diagnostic.html`,
   `share-diagnostic-game.html`, `share-audio-tone.html`).
2. Pages answers `/x.html` with a 308 to `/x`.
3. Since #917 (2026-09-30), the edge middleware answers a path that
   `isUnknownSpaPath` does not know with a 404. It did not know these three.
4. One non-200 entry fails Workbox's install. Every new worker went
   `redundant`, on every deploy, in every browser.

Effects from 2026-09-30 to the fix:

- A new visitor never got a worker, so web push was unavailable to them.
- An existing worker was never replaced. A worker from before the
  network-first handler (installed before 2026-10-01) kept answering every
  navigation from its old precache. A hard reload skips the worker, which is
  why it showed the new build.

What prevents it now:

| Guard | Where |
|---|---|
| HTML in the precache is `index.html` only | `globPatterns` in `client/vite.config.ts` |
| Every `public/*.html` is a known path | `spa-routes.ts`, enforced by `spa-routes.test.ts` |
| The e2e stand-in for Pages has the pretty-URL 308 and the middleware's 404 | `client/e2e/stale-bundle/pages-server.ts` |
| A fresh worker must reach `activated`, and every precache URL must answer 200 (Chromium and Firefox) | `client/e2e/stale-bundle/update.spec.ts` |
| Before production is touched, the build goes to the `precache-check` preview branch and every precache URL must answer 200 there. On failure production keeps its build and the job is red | "Deploy a preview and check its precache" in `deploy-web.yml`, `client/scripts/check-precache.mjs` |
| After the production deploy, the same check on that deployment | "Verify every precached file answers 200 in production" in `deploy-web.yml` |
| Every 10 minutes, every precache URL of the live `pqp.gg/sw.js` must answer 200 (opens an issue) | `sw-precache` in `scripts/monitor/availability.mjs` |
| A worker that fails to install is reported to Faro as `pwa_sw_install_failed`, with the failing `path`, `status`, `reason` (Workbox's error name) and `build` | The worker posts `PQP_SW_INSTALL_FAILED` from its install listener (`client/src/lib/sw-build-script.ts`); the page joins it with the `redundant` state it sees (`installFailureReporter` in `client/src/lib/register-sw.ts`). Every open tab hears it; `onceAcrossTabs` (a Web Lock plus a time in `localStorage`) makes it one event. A worker from before the message reports `reason: unknown` |

Recovery needs no code. A stuck worker still fetches `sw.js` on navigation.
Once the new worker installs, `skipWaiting` lets it take over, and the next
normal reload is on the new build.

To read the reports: in Grafana, Faro events named `pwa_sw_install_failed`.
The `path` and `status` name the file to fix. A burst of them right after a
deploy means that deploy's precache is broken for everybody.

### If a worker itself is broken (the kill switch)

Everything above assumes the new worker can install and take over. If a
shipped worker is broken in a way that keeps the page from working (a fetch
handler that fails every request, for example), the standard remedy is a
"no-op" worker: a `sw.js` with no fetch handler that skips waiting, claims
the open pages, deletes the caches and reloads them. Google's guide:
[Removing buggy service workers](https://developer.chrome.com/docs/workbox/remove-buggy-service-workers).
pqp does not ship one, and does not need to for an install failure like the
one above.

What pqp already has, in order of weight:

1. The update indicator and the automatic safe-moment reload (above).
2. The update ladder (`client/src/lib/update-ladder.ts`): rung 1 deletes every
   cache and navigates with a cache-buster; rung 2 also unregisters the workers.
3. The operator's levers (`client_force_update` on the dashboard announces at once;
   a critical update reloads), which put every out-of-date client through that ladder.

These run in the PAGE, so they need a page that loads. If the worker is so
broken that no page loads at all, ship the no-op worker:

1. Replace the generated worker with a static `client/public/sw.js` that has an
   `install` listener calling `self.skipWaiting()`, and an `activate` listener
   that deletes every cache from `caches.keys()`, calls `self.clients.claim()`,
   and navigates every window client to its own URL.
2. Turn off the PWA plugin's worker generation for that build, so the static file
   is the one served.
3. Deploy, and check `pqp.gg/sw.js` is the no-op file.
4. Keep it live until Faro shows no more sessions on the broken build, then
   restore the generated worker.

## Icons

`scripts/generate-icons.py` renders the whole set from one definition — run it
by hand when the mark changes; Pillow is not a repo dependency and the outputs
are committed:

```bash
python3 scripts/generate-icons.py
```

The mark is a speech bubble with three dots (a typing indicator), drawn rather
than typeset: the wordmark needs Unbounded, which is a webfont a rasteriser
cannot reach, and three letters are illegible at 32px anyway. Maskable and
apple-touch variants are full-bleed and opaque, because each platform applies
its own mask and a pre-rounded source shows as a rounded shape floating inside
it.

The same set is what the Electron app icon should use (still open).

## Not built

- **Web Push.** Notifications only fire while a tab or the installed app is
  running. Real push needs VAPID keys, a subscription store, and a server-side
  sender — a backend feature, not a PWA one.
- **Offline message composition / outbox.** Sends are dropped while offline
  rather than queued for later delivery.
- **Background sync.**

## Watching a share on a phone

A phone in a browser tab cannot give a share the whole screen the way the installed app can, and the two platforms differ:

- **Android Chrome and iPadOS Safari** have element fullscreen. The stage's fullscreen button calls `requestFullscreen()` on the stage container, the browser chrome goes, and `screen.orientation.lock("landscape")` is attempted (Chrome honours it while fullscreen; failures are ignored).
- **iPhone Safari** has no element fullscreen. The button expands the stage in the page (`fixed inset-0`), which fills the web view but leaves Safari's bars. The only true fullscreen there is the native player, `HTMLVideoElement.webkitEnterFullscreen()`, and PR #48 saw it render a MediaStream as black. That path is built (`client/src/lib/fullscreen.ts`) but **opt-in**: set `localStorage["pqp:native-video-fullscreen"] = "1"` on the phone to try it. Call audio is separate `<audio>` elements (`voice-audio-sinks.tsx`), so it keeps playing either way. Verified in emulation only; a real device decides the default.
- **Held sideways** (landscape, under 500px tall) with a share on, the rail, channel list and roster hide and the stage takes the width (`client/src/hooks/use-immersive-stage.ts`); a button in the stage's top bar brings the chat back. The stage controls pad with `env(safe-area-inset-*)` so nothing sits under the home indicator or the notch.
- **Cinema hint**: on iOS in a tab, the stage shows "Add pqp to your home screen for a full-screen cinema" once (`lib/cinema-hint.ts`, see `docs/ONBOARDING.md`).

Pinned by `client/e2e/mobile-immersive-stage.spec.ts` under the `mobile-iphone` (WebKit) and `mobile-pixel` (Chromium) Playwright projects.
