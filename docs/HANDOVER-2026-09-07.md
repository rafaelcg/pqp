## Capacity, measured rather than guessed

The party plateaued near 120 concurrent. **LiveKit was never the limit**: its own
dashboard peaked at 130 against a 1000 allowance. Our join path was the ceiling.

| | Concurrent in one room |
|---|---|
| At the incident (1 vCPU, degraded database) | ~120 to 130 |
| Before the roster deltas | ~225 to 250 |
| **Shipping today, measured three times** | **~350 (range 300 to 400), a floor** |
| Projected with the three PRs in flight | ~650 to 700 |

The media side (500 real viewers on the SFU, single port versus four, the 4 vCPU break between 500 and 600) is recorded run by run in [`docs/CAPACITY.md`](./CAPACITY.md).

The roster delta work bought about 1.4x, not the 3x its description extrapolated.
Measure, do not project. `presence-update` is now about 70% of all bytes on the
wire, which PR #328 addresses.

**The 350 is a floor, not the application's ceiling.** Every simulated client ran
from one laptop over one link measured at 703 Mbit/s, and the runs peaked at 556 to
734 Mbit/s. The wire saturated at roughly the generator's own capacity, so the test
rig may be what ran out rather than the server. It has never been reproduced with
distributed generators. Plan against 350 because it understates, but do not quote
it as the limit. To get a true number, drive load from several machines or measure
egress server-side rather than client-side receipt.

**What runs out is outbound bandwidth**, not processor (24% at the ceiling) and not
the database pool. A single `voice-roster` frame averaged 99 kB. After deltas,
`presence-update` becomes the largest thing on the wire at about 45 kB a frame.

Three mechanisms caused the original ceiling, all three now addressed:
1. Roster fan-out was O(room size) per arrival, to everyone who could see the channel.
2. The client's 12 second join timeout turned a slow room into a retry loop.
   LiveKit counted 552 unique participants in 41 minutes for a room holding ~90.
3. The database was degraded that night, 80 to 240 ms per query, while a join
   cost 19 sequential round trips. It now costs 6.

**Do not cite the old LiveKit load test as capacity.** It drove the media server
directly and bypassed every line of our code, which is why it passed at 150
subscribers while the product was stuck at 120.

## Load testing

Claude owns this. The point is that capacity is a measured number before a watch
party, not discovered during one.

**Safety rules, in order of importance**
1. Never load test production.
2. Staging now has its own Postgres cluster (`pqp-db-staging`, id
   `dzx6qo65q9n0jpv5`, $38/month). It previously shared production's cluster and
   its 100 connection limit, so loading staging could have taken pqp.gg down.
   Never load test staging if that ever changes back.
3. Staging is normally much smaller than production, so scale it to match for a
   run and scale it back afterwards, or the number is meaningless.

**The harness** is `server/scripts/load-fanout.ts` with a README beside it, and
the procedure is documented in `docs/STAGING.md`. It must include the HTTP
bootstrap and the voice token call, or it measures something far cheaper than a
real arrival: a cold browser costs roughly a hundred pool checkouts.

**Accounts** come from a `LOAD_TEST_TOKEN` secret set on `pqp-api-staging` only,
value in `~/.config/pqp/staging-load-test.env` (0600). It is refused on
production, guarded by the Fly app name rather than `NODE_ENV`, because the
container hardcodes `NODE_ENV=production` and staging would otherwise be
indistinguishable. Verified: the same header returns 200 on staging, 401 on
`api.pqp.gg`.

**Rerun it** before any expected watch party and after any change to the join path.

**Correction on item 2.** The plan assumed people outside a call only need an
occupancy count. That is not implementable as the client stands: `channel-list.tsx`
draws every occupant of every voice channel with avatar, name and mic, deafen,
screen and camera badges for channels the viewer has not joined, and
`members-panel.tsx` reads per-person mute state for channels a moderator is not in.
`client/e2e/voice-state-badges.spec.ts` pins exactly that. So the saving is rate,
not shape: people in the call keep a 10 second keyframe because their roster is the
signalling allowlist, the audience moves to 30 seconds because theirs is only a
badge. Nothing on the wire changed, so no client compatibility risk at all.

**Measured, presence deltas plus the audience split**, 400 sockets with 300 in one
room, before and after on one binary:

| | Before | After |
|---|---|---|
| Presence bytes | 845 MB | 49 MB |
| Everything written | 1,104 MB | 311 MB |
| Per socket | 92.6 KB/s | 26.1 KB/s |

Outbound grows as roughly N^1.72 before and N^1.57 after. **Projected ceiling
350 to 375 becomes roughly 650 to 700**, labelled a projection because this same
arithmetic overestimated the roster work.

**Next bottleneck after these land: `typing-broadcast`**, the largest single frame
type once keyframes shrink, then the remaining participant fields in roster
keyframes.

**Measured, WebSocket compression (#331)**, 400 sockets with 300 in one room:

| | Plain | Compressed |
|---|---|---|
| On the wire | 953 MB | 320 MB (3.0x) |
| CPU | 9.1% of a core | 25.3% |
| Peak memory | 194 MB | 371 MB |

Three times fewer bytes for about two and a half times the processor, on a machine
that runs out of bytes first. **Kill switch: `WS_COMPRESSION=off`.** Every client
negotiates it, including iOS and Android; anything that does not simply stays
uncompressed. Do not set `serverMaxWindowBits` or `clientMaxWindowBits`: a value in
either makes the library reject the handshake with a 400 for any client that did
not offer the matching parameter, which is four clients out of five.

**Trimming the participant payload is not worth doing.** Omitting every safely
omittable field saves 44% raw but only 8% after compression, because a compressed
roster is 69% identity (peer id, user id, display name) and those cannot go: both
native decoders fail without them. Numbers are in `server/scripts/README.md`.

**Operational trap found while testing:** exceeding Fly's `hard_limit = 600`
connections produces `could not find a good candidate ... at load balancing`, which
reads exactly like a dead API but is the proxy. A machine restart clears it.

## Watch this: roster delta adoption

`GET /api/admin/metrics` carries `voice.roster` with `deltas`, `snapshots`,
`sockets` and `socketsOnDeltas`.

**These counters are per process and reset on every deploy.** A reading is only
true until the next restart. This trap has already caught one investigation.

**An API restart does not refresh a browser.** It reconnects with the bundle it
already has, so a negotiated wire change starts at zero adoption on a perfect
deploy and climbs only as people reload the page. `socketsOnDeltas` at 2 of 28
shortly after a deploy is expected, not a fault.

**Correction: `deltas` was 0 in production because the server never sent any,
not because of old tabs.** `server/src/ws/voice.ts` had
`const delta = registryOn() ? null : foldRoomEvents(events)`, and production
and staging run with `VOICE_REGISTRY=postgres`. So on the machine that
mattered, every roster change still went to every audience socket as a whole
`voice-roster`, the exact size-times-audience product the deltas were written
to remove; the delta tests were green because they ran with the registry off.
The 1.4x measured for "roster deltas" above was the keyframe split and the
coalescing, not deltas. Fixed in the roster-deltas-registry-mode PR: with the
registry on the delta is now a diff of the rows against what the process last
sent, so a change made on the other machine becomes a delta too. That PR is
`restarts-api` and lands with the next API deploy.

**The alarm condition, after that deploys.** Deltas must climb within minutes
on any active room whose viewers run a build that negotiates the cap (web and
Electron since the delta deploy, iOS build 19, Android with its delta build).
If `socketsOnDeltas` is a healthy fraction, `activeRooms` is above 0, and
`deltas` stays at 0, that is the alarm: the diff path is not running. Zero is
still correct with no room active or nobody negotiating. Confirm the running
version is the one with the fix before reading the counter (per process, reset
on deploy). The rollback is the previous image, which sends whole rosters and
is slower but correct.

## The two things that were silently broken

Both fixed. Both made bug reports misleading, because people were reporting
problems already fixed in builds they could not get.

1. **Android testers could not install updates.** The signing key lived in a
   GitHub Actions cache that expires after seven days, so it rotated silently and
   Android refuses an update signed by a different key. There is now a durable key
   in repository secrets, backed up at
   `~/.config/pqp/android-sideload-keystore/`, and the workflow fails loudly if it
   is missing.
2. **iOS external testers were a month behind.** Uploading a build does not put it
   in the public TestFlight group; it must also be submitted for review and added.
   Builds 12 to 17 reached nobody outside the team. Build 18 shipped 2026-09-07.
   **Build 19 is needed** to deliver the iOS roster delta work.

  month, against 5 TB. Four watch parties would add about 1.2 TB. The 2% figure on
  Vultr's dashboard is against a prorated allowance and includes load testing.
- **SSH is hardened**: password login off, fail2ban running. Failed attempts went
  from 5,370 a day to zero. Two keys exist; the break-glass one is at
  `~/.config/pqp/sfu-breakglass`, passphrase-protected, passphrase in Rafael's
  Passwords app. **Losing both keys means a Vultr console session or a rebuild.**

  range and removing it breaks relayed calls. A relay socket only exists while an
  allocation is live, so the range looks empty most of the time.
