“One-click Discord transfer” — feasibility spike

What is actually possible in August 2026 for moving a Discord server into pqp, what it costs, what it legally exposes you to, and the two-day version that captures most of the value.

2026-08-08 · researched against Discord's live developer docs and the pqp codebase at launch/p0-hardening

Verdict
Build the structure-only importer now (~3 agent-days). Do not build message-history import — probably ever.

Copying channels, categories and ordering is cheap, legally clean, needs no bot and no Discord approvals, and it is the part that actually removes the “ugh, I’d have to rebuild everything” friction. Copying message history costs 10× more, requires a privileged intent under annual re-review, forces you to break an invariant s3.ts deliberately documents, and makes you the LGPD controller for thousands of strangers’ messages and unscanned images — while CONTENT_SCAN_PROVIDER is still empty.

01What “one-click” would have to mean

“Transfer my Discord server” is four separable products wearing one button. Ranked by value-per-unit-of-pain:

The rest of this doc is mostly about proving that the cheap row is genuinely cheap and the expensive rows are genuinely expensive.

02Route A — Guild Templates: structure with zero bot

This is the finding that changes the shape of the whole project, and it is not what anyone expects when they hear “Discord import.”

Discord has a first-class, supported Guild Template resource. A server admin with MANAGE_GUILD creates one from Server Settings and gets a link like discord.new/AbCd1234. Anyone can then read that snapshot:

GET https://discord.com/api/v10/guilds/templates/{template.code}

The response contains a serialized_source_guild object holding the entire structural skeleton of the server:

In the templateNot in the template
Guild name, description, icon hash, locale, verification level
All channels: name, type, position, topic, parent_id, nsfw, bitrate, rate_limit_per_user
All categories (they are just type: 4 channels)
All roles: name, colour, permissions bitfield, hoist, mentionable
Per-channel permission_overwrites, referencing template-local role ids
AFK / system channel wiring 		Members — none at all
Messages — none at all
Attachments — none
Custom emoji and stickers — not included
Webhooks, integrations, bans, invites
Why this is the right primitive

It is exactly the subset pqp can usefully receive, and it is a subset containing zero third-party personal data. No member names, no message bodies, no avatars. The only personal data involved is the admin's own act of pasting a link. Every LGPD, Developer-Policy and content-scanning problem in this document evaporates on this route.

Practical notes and caveats I'd want verified against the live API before shipping:

  • Auth: Discord's docs list no auth requirement on GET /guilds/templates/{code}, and in practice it behaves as a public read. Assume you may still need a bot token in the Authorization: Bot … header — that's a token in Railway env, not a bot in the user's server, and requires no verification and no privileged intents. Test both before committing to the copy on the landing page.
  • Snapshots go stale. A template is frozen at creation unless the admin hits “Sync.” Show the template's updated_at in the preview so nobody imports a six-month-old layout and blames you.
  • One template per guild in the UI, and creating one requires MANAGE_GUILD — which is the correct authorization gate for “copy my server's shape somewhere else.” The permission check is done for you, by Discord, for free.
  • It's a paste, not an OAuth dance. No redirect URIs, no client secret, no consent screen, no app review. The user pastes a URL. That is genuinely one click plus one paste.

The privileged-intent gate is the load-bearing constraint

Two of the three privileged intents are exactly the two you'd need, and one of them bites harder than most people realise:

The trap

MESSAGE_CONTENT gates REST responses, not just Gateway events. Without it, GET /channels/{id}/messages returns message objects with content, embeds, attachments and components emptied out. This is a long-standing, well-documented behaviour — see discord.py #7661, where channel.history() returns contentless messages. You cannot sidestep the intent by “just using REST.”

The 2026 rules, which changed recently and in your favour:

10,000
users, new review threshold
As of 10 June 2026 the privileged-intent review trigger moved from “100 servers” to “10,000 unique users reached.” Below that you self-enable in the Developer Portal. A day-0 importer is comfortably under it.
90
days to submit, once notified
You keep working while under review. Approval needs a specific use case, minimal intent requests, and a written data-retention story.
annual
re-application
Existing access must be reapplied for every year. This is the part to hate: a launch feature whose continued existence depends on a yearly review of a data-retention policy you'd rather not have.
100
servers → bot verification
A separate process from intent review, unchanged. If the importer succeeds at all, you cross this and inherit an ID-verification and review workflow.

Read that grid as a sentence: message-history import is a feature that requires you to annually justify to Discord why you retain Discord message content, in order to help people leave Discord. That is not a fight worth having for a hobby project, and it's not a fight you win by being clever about it.

04Rate-limit math for a 10k-message server

The rate limits are real but they are not the bottleneck, and it's worth being precise because the internet assumes otherwise.

Discord's published limits: 50 requests/second globally per bot, plus per-route buckets keyed by top-level resource (so /channels/A/messages and /channels/B/messages have independent budgets). Responses carry X-RateLimit-Limit, -Remaining, -Reset-After, -Bucket, -Scope; a 429 carries retry_after in seconds (fractional) and a global flag. Separately, 10,000 invalid requests per 10 minutes per IP (401/403/429) gets your IP temporarily blocked — but 429s tagged X-RateLimit-Scope: shared don't count against you.

The arithmetic

Server:  40 channels, 10,000 messages total, ~250 members

structure    GET /guilds/{id}/channels            1 request
roles        GET /guilds/{id}/roles               1 request
emoji        GET /guilds/{id}/emojis              1 request
members      10,000 / 1000 per page              10 requests   (needs GUILD_MEMBERS)
messages     10,000 / 100 per page              100 requests   (needs MESSAGE_CONTENT)
                                                ------------
                                                113 requests

at the 50 rps global ceiling                      2.3 seconds
paced politely at 5 rps                          ~23 seconds
So what

A 10k-message server is 113 API calls. That is not a rate-limiting problem; it is a rounding error. Anyone who tells you Discord's rate limits make history import hard is wrong about which resource is scarce. The scarce resources are bytes (attachments) and your own reliability (a Railway redeploy mid-import, with no job table to resume from).

Where it does get uncomfortable: pagination is strictly sequential per channel (each page's oldest id becomes the next before), so a single 200k-message channel is 2,000 serial round-trips — maybe 7–10 minutes of wall clock with backoff. Fan out across channels, not within one.

05Attachments: the signed-CDN-URL problem

Since December 2023, every Discord CDN attachment URL is signed:

https://cdn.discordapp.com/attachments/{channel}/{message}/file.png?ex=<hex>&is=<hex>&hm=<hmac>

ex  hex unix timestamp — when this URL stops working
is  hex unix timestamp — when it was issued
hm  HMAC over the above

Strip the params, or let ex pass, and you get a 404 “This content is no longer available.” Signatures are short-lived (widely reported as ~24h from issue; Discord's docs decline to commit to a number). Discord refreshes them automatically for URLs it renders in its own client, and it will re-sign a bare CDN URL you pass into an embed or a webhook avatar_url.

This kills hotlinking outright. A pqp message whose image points at cdn.discordapp.com is a 404 by tomorrow. There is no “just link to Discord's copy and save on storage” option — the option people assume exists does not exist. You either copy the bytes or you show nothing.

And copying the bytes fights pqp's architecture

From server/src/lib/s3.ts, line 13, in the file's own header comment: “No object bytes ever pass through this process — the browser PUTs and GETs.” That is a deliberate, load-bearing invariant. The module exports presignPut, presignGet, headObject, deleteObject — and no upload function at all. Meanwhile server/src/lib/safe-fetch.ts caps response bodies at MAX_BODY_BYTES = 512 * 1024 with a 5s timeout, because it exists to fetch OpenGraph tags, not media.

So a history import needs you to: add a server-side putObject, add a large-body fetch path that bypasses the 512 KB cap, add cdn.discordapp.com to a host allowlist, and then hold hundreds of megabytes of streaming I/O inside the same process that serves the API and the WebSocket. Each of those is individually fine. Together they undo the thing that currently makes pqp's attachment story simple enough for one person to reason about.

The one that should end the conversation

docs/HANDOVER.md lists the CSAM / OSA compliance gap as priority #4, with CONTENT_SCAN_PROVIDER still empty. History import means volunteering to permanently host several hundred megabytes of unreviewed images from a community you know nothing about, in your R2 bucket, under your name, with no scanning. Structure-only import stores zero bytes. This asymmetry is not close.

06Route C — Discord's Data Package (and why it doesn't help)

Discord's Request all of my data flow (Settings → Privacy & Safety) emails a ZIP. It is a genuine, GDPR/LGPD-shaped export and it is completely wrong for this job.

What's in itWhy that's not a server migration
Your own messages, as JSON per channelOnly yours. Nobody else's. A channel restored from your package is a monologue — you talking to yourself for three years. It reads as broken, not nostalgic.
A channel-id → channel-name mapNames only. No types, no categories, no ordering, no topics, no roles. You cannot reconstruct a server's shape from it.
The list of servers you're in (id + name)Names, not contents.
CDN links to files you attachedUnsigned links to a CDN that now requires signatures. Mostly dead on arrival.
Activity folders + an analytics fileIrrelevant, and radioactive to ingest. Do not ask users to upload their Discord analytics to you.

Plus the operational killer: Discord states the request can take up to 30 days. No onboarding flow survives “come back in a month.” The Data Package is the right tool for a person archiving their own past, and the wrong tool for a community changing address. Ignore it.

07Route D — user tokens / self-bots: the ban route

The technically-easiest path is to have the admin paste their own Discord user token. Their account already sees every channel; no bot, no intents, no OAuth, no review. Every “server cloner” on GitHub works this way.

Do not do this. It is unambiguously prohibited: automating a normal user account outside the OAuth2/bot API is against Discord's ToS and API terms and results in account termination. Even DiscordChatExporter — 11.7k stars, the most legitimate tool in this space — ships the warning in its README:

> [!WARNING]
> While DiscordChatExporter allows it, automating user accounts is against
> Discord TOS and may result in you getting banned.
> If possible, use a bot to export chat logs from accessible channels.

The asymmetry is what matters: the person who gets banned is your user, not you. Shipping a feature whose failure mode is “the community leader who championed pqp loses their Discord account” is a launch-ending story in a market that runs on word of mouth. There is no version of this that is worth it.

Gap in this research — read before shipping Route B

I could not read the current Discord Developer Policy text: discord.com/developers/docs/policies-and-agreements/developer-policy now 301s to docs.discord.com, which 307s to support-dev.discord.com, which returns 403 to automated fetchers. So I cannot tell you what it currently says about retention limits, bulk collection, or using Discord data to move users to a competing service. If Route B ever gets serious, someone has to read that document with a human browser first. Do not let this doc stand in for it.

Brazil / LGPD

Structure-only import processes no third-party personal data, so this section is entirely about Route B. If you import message history:

  • You become the controller of other people's data on someone else's say-so. The consent you collected came from the server admin. The data subjects are the 250 members whose messages, usernames and avatars you just copied. The admin cannot consent for them. Legitimate interest (legítimo interesse) is arguable but it is an argument you'd have to be prepared to make.
  • Concrete obligations attach immediately: LGPD data-subject requests answered within 15 days, breach notification to the ANPD within 72 hours, and a lawful basis documented per processing activity — for a dataset you neither generated nor understand.
  • The enforcement climate got worse. The ANPD moved from guidance-issuing to active enforcement across 2024–2025; 2026 is a materially more demanding environment than 2023 was.
  • Portability doesn't rescue you. LGPD does grant portability, but it's the subject's right over their own data, and the ANPD hasn't finished regulating it. It is not a licence to bulk-copy a community.

Per MEMORY.md: this is a solo hobby project at day-0 scale, so size this down — nobody is auditing pqp next quarter. But the point isn't fine risk. It's that Route B is the one feature that turns a hobby project into a data controller for strangers, and it does so at launch, for a feature users will barely scroll through.

09What pqp already has to receive an import

Already there, and better than expected

PieceWhereImport-readiness

It already carries createdAt, editedAt, authorId, replyToId, pinnedAt, storageKey. Make the Discord adapter emit this shape and the importer becomes format-agnostic — pqp→pqp migration and Discord import become the same code path.
Discord-wire-compatible webhook ingest POST /api/webhooks/:id/:token (unauthenticated, token-in-URL, matched pre-auth at api/index.ts:3139); services/webhooks.ts; snake_case executeWebhookSchema in packages/shared/src/webhooks.ts Genuinely useful — for bridging, not importing. Watch the ordering rule: position is scoped by (parent_id, type) at top level and by parent_id inside a category — not globally like Discord's.

Author spoofing users.is_webhook, synthetic clerk_id = 'webhook:<uuid>', per-message webhook_username / webhook_avatar_url The mechanism exists and is already excluded from user search and mention resolution. Historical authors would ride on this.
Attachment plumbing services/attachments.ts — presign PUT → browser PUT → headObject verify → claim in the message txn Browser-PUT only. Fine for a client-driven import; blocking for a server-side one.

Missing, and each one is a real build

  1. A bulk-insert path. There is no batch create route anywhere. createServer hard-codes exactly two channels in one transaction; everything else is one POST /api/servers/:id/channels at a time against writeLimiter (capacity 30, refill 2/s) — so a 40-channel import driven through public routes takes ~20 seconds of self-inflicted throttling. The importer needs its own service function doing one multi-row insert in one transaction.
  2. Historical timestamps. Nothing in the codebase passes created_at. Both insert paths (createMessage in services/messages.ts:446, reachable only from the WS message-create branch, and executeWebhook) stamp NOW(). There is no HTTP POST route for messages at all.
  3. Server-side byte upload. putObject does not exist, by design (§05).
  4. A job with a memory. There is no queue, no worker, no job table — only unref'd setInterval sweepers inside the API process. A Railway redeploy mid-import strands it with no resume. The closest precedent to copy is sweepPendingAccountDeletions: a durable marker column plus a 5-minute claim loop that finishes interrupted work.
The shape of the answer

Structure-only import needs exactly one of those four (bulk insert). History import needs all four, plus the intent, plus the scanner. That 1-vs-4 split is the whole recommendation.

10The pragmatic v1 design

Name it honestly. Not “Import your Discord server” — that promises history and people. Call it “Copy your Discord layout” / “Copie a estrutura do seu Discord”. Under-promise in the button, over-deliver in the 20 seconds it takes.

Flow

  1. Admin pastes a discord.new/<code> template link (with inline instructions for creating one: Server Settings → Templates → Copy Link).
  2. POST /api/import/discord/preview — server fetches the template, parses it with a Zod schema in @pqp/shared, maps it, returns a tree plus a plain-language list of what will be dropped. No writes.
  3. User unchecks whatever they don't want and confirms.
  4. POST /api/import/discord/apply — one transaction, one multi-row insert, done in under a second. Then hand back an invite link and pre-written text to paste in Discord.

Why roles are shown, not mapped

Discord's model is 250 additive permission bitfields with per-channel overwrites. pqp's is a three-value TEXT enum on server_members.role, with no roles table and no overwrites (DISCORD_GAPS #22 is the unbuilt design, and it's flagged as the largest open item). Any automatic mapping is a lossy privilege decision made by an importer: a Muted role becomes a full member; a Trial Mod with two permissions becomes either a nobody or a full admin. Silently changing who can do what is the worst possible first impression. Show the role list, map nothing, let the human choose. This costs half a day and saves you the one bug class that would make an admin quit.

Why members are not copied — the honest version

Not “we chose not to.” It is not possible, and it wouldn't work if it were.

  • The API gives you Discord user ids, usernames and avatar hashes. It does not give you email addresses. There is no mechanism by which a Discord user becomes a pqp user without that user showing up and authenticating with Clerk.
  • Minting 250 shell accounts produces a member list of ghosts who can't log in, can't be DM'd, and make the server look emptier than an honest empty server. It also means processing 250 people's names and faces because a third party clicked a button.
  • The thing that actually moves people is one message in the old server from someone they trust. So make that the product: after import, hand the admin an invite (server_invites, already built) plus copy-pasteable pt-BR text, and track redemptions. That's your conversion funnel, and it's measurable in a way “we copied a member list” never is.

Attachments: neither. Recommend showing nothing.

You asked re-upload vs hotlink. The honest answer for v1 is neither, because there are no messages to attach to — and if there were: re-upload, never hotlink. Hotlinking cdn.discordapp.com is a guaranteed 404 within a day (§05), so it isn't a cheaper option, it's a broken one. Re-uploading is correct and unaffordable: it needs putObject, a large-body fetch path, a CDN-expiry race, and content scanning you don't have.

The v1.5 worth more than history import

Bridge mode — flagged, not recommended yet

pqp's incoming webhooks are already Discord-wire-compatible with username / avatar_url per-message override. A small bot that relays new Discord messages into pqp via POST /api/webhooks/:id/:token would make a freshly imported pqp server look alive on day one, and let a community drift over instead of jumping. It reuses the existing ingest endpoint with zero new ingest code, and it never stores history — only live traffic, forward-only. That's a much better use of the same effort than backfilling 2019.

The catch is the same catch: relaying message content needs MESSAGE_CONTENT. Ship structure-only first, see whether anyone even asks, and only then decide whether bridging is worth taking on a Discord app with an annual review.

11User journey walkthrough (v1, realistic)

Marina runs Cafofo Gamer — 380 members, 22 channels across 5 categories, 3 voice rooms, two staff-only channels. She found pqp on Twitter and is curious but not committed.

  1. pqp · /app, empty state Alongside “Create a server” there's a second, quieter option: “Copiar a estrutura do meu Discord”, with the subtitle “canais e categorias — sem mensagens, sem membros”. The subtitle is the whole trust strategy. She knows exactly what she's getting before she clicks.
  2. pqp · import dialog One field, and a three-step instruction with a screenshot: Discord → Server Settings → Templates → Create Template → Copy Link. No OAuth screen, no “pqp wants to read your messages,” no bot to approve. She pastes discord.new/kR2mF9xQ.
  3. Discord Creating the template required her MANAGE_GUILD permission — Discord did the authorization check, so pqp never has to ask “are you really the admin?”
  4. pqp server · preview, ~400ms POST /api/import/discord/preview. She sees her sidebar, rendered as her sidebar: 5 categories, 22 channels, right order, emoji intact in the names. Checkboxes on everything. Two channels carry a privado chip. Above the tree, a snapshot date: template created 3 days ago.

    Below it, a plainly-worded “o que não vem” panel — messages, members, the 14 roles (listed by name, greyed out), custom emoji, and one line noting #duvidas is a forum channel that will land as a normal text channel. Nothing hidden, nothing spun.
  5. Marina She unchecks #bots-spam and a dead 2023 event category. Hits Criar servidor.
  6. pqp server · apply, one transaction POST /api/import/discord/apply: one servers row, one server_members row (her, owner), one multi-row insert of 18 channels with recomputed contiguous position per (parent_id, type) group, and channel_members rows putting her alone in the two private channels. Under a second. No job table needed because there is no job — it's one write.
  7. pqp · done screen Her server, looking like her server. Then the actual ask, which is the point of the whole feature: an invite link, a Copiar convite button, and pre-written Portuguese to paste in Discord — “galera, montei nosso espaço no pqp, tá tudo igual aqui: {link}”. Plus one honest line: “seu Discord continua lá — nada foi alterado nem apagado.”
  8. Discord → pqp She pastes it in #geral. Over two days 40 people join. She keeps both open for three weeks. Whether pqp wins is now about voice quality and whether her friends stay — which is the right thing for it to be about, and is exactly what a history importer would have obscured.

Note what didn't happen: no consent screen, no bot in her server, no 30-day wait, no privileged intent, no bytes copied, no strangers' data in your database, and no support ticket titled “the import stopped at 60%.”

13Failure modes

Route A can actually hit these

  • Template is stale. Snapshot from months ago; admin blames pqp for “losing” channels. Mitigation: show the template's date prominently in the preview.
  • Template doesn't exist / was deleted / code typo. Discord returns 404 for a code that was valid yesterday. Mitigation: distinct copy for each of unknown-code, network-failure, and malformed-URL. A generic “something went wrong” here loses the user permanently.
  • Hostile template. Nothing stops someone crafting a template with 400 channels, 100-char names, and 4KB topics, then feeding it to your unauthenticated-ish preview endpoint. pqp has no channel-count cap of its own. Mitigation: hard caps in the mapper (say 200 channels, 30 categories), reject above with a clear message, and rate-limit preview per user.
  • Private-channel misclassification. The one that matters. Discord's overwrite model is richer than a boolean, and an ambiguous case resolved toward public leaks a staff channel's existence and future contents. Mitigation: fail closed, always; unit-test the ambiguous cases; say “private” in the preview so a human can catch it.
  • Position scrambling. Copying Discord's global positions into pqp's per-(parent_id, type) scheme produces a sidebar in the wrong order — subtle, and it silently undermines “it looks just like your Discord.” Mitigation: sort-then-renumber, with a test.
  • Discord changes or removes the template API. Low probability, total feature loss, zero warning. Mitigation: none available. Accept it — this is a 4-day feature, not a 20-day one, which is part of why 4 days is the right number.

Route B's, for the record

  • Process restart mid-import. A Railway redeploy at 60% leaves a half-populated server and no way to resume. This is far more likely than rate limiting and there is no infrastructure to catch it.
  • Rate limiting mid-import is real but survivable — honour retry_after and X-RateLimit-Reset-After, back off per bucket, and remember 429s with Scope: shared don't count toward the 10k invalid-requests ban. The failure mode isn't the 429; it's a naive client that retries into an IP block.
  • Huge servers. Discord permits 500 channels. A 2M-message server is ~20,000 serial paginated calls and tens of gigabytes. There is no graceful version of this; you'd need a hard message budget (MAX_EXPORT_MESSAGES = 50_000 in export.ts is the existing precedent) and to be blunt about it in the UI.
  • Emoji. pqp has no custom emoji at all. Every <:pepehands:123> in imported text renders as literal garbage, and custom-emoji reactions can't be represented — reactionEmojiSchema caps at 32 chars and rejects the token form. An imported history is visibly mangled, not merely incomplete, which is worse than not having it.
  • Mentions and Discord-only markup. <@123>, <#456>, <t:1700000000:R>, ||spoilers|| — all need rewriting or they leak raw tokens into the transcript.
  • Attachment expiry race. Long imports outlive their signed URLs. Mid-import 404s on files that existed when you enumerated them.
  • Unscanned media at rest. Covered in §05. This is the real one.

14Decision, and what would change my mind

Build now
Structure-only import via Guild Templates. ~4 agent-days.

Because it removes the single largest reason an admin won't try pqp, needs no bot, no OAuth, no privileged intent, no Discord review, no bytes, and no strangers' personal data — and because it converts into the thing you actually want, which is an invite link pasted into a live Discord channel by someone people trust.

Build never (as currently specified)
Message-history import.

Because it costs ~13 more agent-days, undoes s3.ts's no-bytes-in-process invariant, requires a job system pqp doesn't have, needs a privileged intent renewed annually, makes you the LGPD controller for hundreds of strangers, obliges you to permanently host hundreds of megabytes of unscanned images while CONTENT_SCAN_PROVIDER is empty — and delivers a transcript visibly broken by missing custom emoji and unresolvable mentions, which nobody will scroll.

What would change my mind on history

  • Real demand, counted. Ten admins who completed a structure import asking unprompted for history. Not one loud request — ten.
  • Content scanning live. CONTENT_SCAN_PROVIDER configured and proven. This is a hard gate, not a preference.
  • Custom emoji shipped (DISCORD_GAPS #26). Without it an imported history is disfigured, and a disfigured history is worse marketing than no history.
  • A real job system. Which PLAN_STATUS open item 5 already wants for scaling past one instance — so if that lands for its own reasons, one of history import's four blockers disappears for free.

Even then, I'd build bridge mode (§10) before backfill. Making a new server look alive today beats making it look old.
