Ambient life

A maintainable, scalable system for running AI personas inside pqp servers, so the five communities we advertise at launch have people in them. Architecture, the production identity problem, a cost model in dollars, and the honesty question addressed rather than dodged.

2026-08-08 · grounded in server/src/ws/chat.ts, server/src/services/webhooks.ts, server/src/auth/clerk.ts · working prototype in tools/ambient/

Recommendation
Build it as framed characters — o elenco da casa — not as undisclosed humans. Ship it as a standalone in-repo service (tools/ambient/) driving the real HTTP + WebSocket protocol with server-minted character accounts.

The money is not the constraint: five servers of believable chatter on Claude Haiku 4.5 costs ~$2.50/month, and fifty costs ~$25. The constraints are (1) production identity — DEV_AUTH_BYPASS is refused under NODE_ENV=production, so there is no account to post as until we build one; and (2) trust, which is spent once and cannot be re-earned. Undisclosed personas in servers we advertise as evidence of activity is a prática enganosa under CDC art. 37 and a policy violation on both app stores — for a benefit that framed characters deliver anyway, because Orkut-era Brazil already loved a cast.

The prototype makes the choice reversible on purpose. Disclosure is a per-persona string in YAML; flipping it to undisclosed is a one-word diff. I am recommending against that word, not removing it.

01What pqp already gives you — and the three things it doesn't

Everything below was read out of the tree at launch/p0-hardening, not assumed. The good news is that the protocol a persona needs is already complete and already exercised by a raw-protocol harness (scripts/chat-load.mjs) — so a runner is a client, not a feature.

The backfill finding, stated plainly

Checked, and the answer is no

There is no way to set created_at through the API. createMessage() takes (channelId, author, body, replyToId?, attachmentIds?) and the INSERT never names the column; executeWebhook() is the same. No route, no frame, no admin path. So "generate two weeks of dated history via the API" is not a thing that can be built — ambient life starts live-only.

The escape hatch is SQL. server/src/services/export.test.ts and retention.test.ts both write INSERT INTO messages (…, created_at) VALUES (…, NOW() - INTERVAL '1 hour'), so the column accepts a value fine — a backfill script would need DATABASE_URL and would run against the production database directly. That is a real operation, not an impossible one, but it is a one-off migration with production DB access, not a mode of the runner, and it should be reviewed as such. Recommendation: do not build it for v1. Start the servers two weeks before launch and let the history be real.

Webhooks: what they can and cannot do

server/src/services/webhooks.ts is more interesting than it looks. Creating a webhook mints a real users row with is_webhook = TRUE and a synthetic clerk_id of the form webhook:<uuid> — the comment says it outright: "nothing ever authenticates as this row, so it only has to be unique, not real." That is a pseudo-identity primitive that already exists in the schema, and §02 builds on it.

As a posting mechanism, though, webhooks are the wrong tool for this job, and it is worth being exact about why:

Webhook canWebhook cannot
Post as a name + avatar with no account (POST /api/webhooks/:id/:token, unauthenticated — the URL is the credential) Show a typing indicator
Appear live — the route calls broadcastToChannel, so messages fan out over WS exactly like a real one Add a reaction, or be reacted to by a profile popover (the client disables it for webhook messages)
Rate-limit itself (20 burst / 1 per second per webhook id) Appear in the member list, in presence, or in a voice channel
Carry embeds Reply to a message, join a thread, or read the channel at all
The disqualifier is one line of the client

client/src/components/chat/message-list.tsx renders a WEBHOOK badge on every webhook message, titled "Posted by a webhook, not a member." That is excellent if you want soft disclosure for free — and fatal if you want a community that looks inhabited, because a server whose entire population is badged "not a member" reads as an RSS feed. Webhooks also cannot react, cannot show typing, and never appear in the member list, so the three cheapest signals that a room has people in it are all unavailable.

Verdict: webhooks are the right primitive for a bot — a scores bot, a "novidades" feed — and they should be used for exactly that. They are the wrong primitive for a persona.

02Identity in production: the decision that blocks everything

Locally this is solved: DEV_AUTH_BYPASS=true plus dev-local-token:<suffix> mints a distinct account per suffix (server/src/auth/clerk.ts, devBypassIdentity), and the prototype uses exactly that. In production it is solved by nothing: isDevAuthBypassEnabled() returns false under NODE_ENV=production, and assertAuthConfig() makes the process fail at boot if the flag is set there. That is correct security and it is a hard wall.

Three options. They are not equally good.

Option A

Webhook-based posting reject

No new auth surface, no accounts, works today in production.

Genuinely tempting: zero new code, zero new credentials in the auth chokepoint, and messages already broadcast live. But §01's table is the whole argument against it — no typing, no reactions, no presence, no member list, no replies, and a permanent WEBHOOK badge on every line. You would be advertising five servers whose members list is empty and whose every message is labelled "not a member".

Keep it for what it is for. One webhook per community posting a genuinely useful automated thing (a match-day scoreboard, a patch-notes feed) is good content and honest by construction. It is not ambient life.

Option B

Operator-owned real Clerk accounts viable, unpleasant

25 real accounts, provisioned through the Clerk Backend API.

CLERK_SECRET_KEY is already on Railway, and the Clerk Backend API can create users programmatically and mint sign-in tokens — so this is not manual signup 25 times. The server verifies whatever the runner sends through the ordinary verifyToken() path, which means zero changes to pqp.

What it costs. Every persona becomes a billable Clerk MAU and a row in the real user directory — enumerable through user search like any other account, which is fine, but also deletable, bannable, and subject to every account lifecycle path in the product. Token refresh becomes the runner's problem, and Clerk session tokens are short-lived. And it puts 25 sets of real credentials in an environment file.

Unverified assumption needs a half-day spike: that a Backend-API-minted session token satisfies verifyToken(token, { secretKey, authorizedParties }) with the azp claim the server expects. Confirm that before committing.

Option C

Server-minted character accounts recommended

The concept the schema already half-implements.

Webhooks already create a users row with a synthetic clerk_id that nothing authenticates as. A character account is that row plus one thing: a long-lived bearer token that does authenticate as it. Concretely:

  • A character_accounts table: user_id, a hashed token, created_by, revoked_at. The users row carries clerk_id = 'character:<uuid>' and a new is_character flag — not is_webhook, which would inherit the client's badge and the disabled profile popover.
  • One branch in verifyAuthHeader(), ahead of the Clerk path and behind an explicit env gate (CHARACTER_ACCOUNTS_ENABLED), looking up the token hash.
  • The age gate is satisfied at creation by writing age_checked_at / age_check_passed directly — a character has no date of birth to declare, and leaving it pending would close its socket with 4401.

Why this and not B. It is provisionable by script at any scale (§06 needs 250 of these), it costs nothing per account, it is revocable in one UPDATE, and — the part that matters most — it makes "this is a character" a fact in the database rather than a convention in a config file. Once is_character exists, the disclosure UI in §03 is a rendering decision the client can make honestly, and moderation can treat the cast as a class.

What it costs. A new credential type in the single most security-sensitive function in the server. That is not free and it must be reviewed as auth work, not as tooling: tokens hashed at rest, never logged, scoped so a character can only act inside servers it is a member of, and explicitly excluded from account-deletion and data-export routes. Budget it as ~2 days including review, not an afternoon.

Sequencing

The prototype runs on the dev bypass and therefore proves everything except this. That is deliberate — the identity decision is a product and security decision, not something a spike should quietly pick. Nothing ships to production until Option C (or B) is built and reviewed.

03Architecture

In-repo, out of the workspace

The runner lives at tools/ambient/, in the pqp repo but not in pnpm-workspace.yaml. That combination is deliberate:

  • In the repo, because the personas are content the product's voice depends on, the runner is a first-class consumer of the WS protocol, and a protocol change that breaks it should break it in the same PR. A separate repo means the ambient system silently rots the first time a frame changes.
  • Out of the workspace, because it is a service with its own lifecycle, its own npm install, and its own deploy. Root pnpm test, pnpm build and pnpm typecheck iterate workspace packages, so none of them touch it — CI is unchanged.

Runtime: plain Node ESM, Node 22+. Two dependencies at most — js-yaml, and @anthropic-ai/sdk as an optional dependency loaded by dynamic import() only on the live path, so canned mode and every unit test run with it absent. fetch and WebSocket are Node globals; nothing else is needed.

Deploy: a Fly machine or a systemd unit running runner.js --watch per shard. Not cron — the runner needs a persistent WebSocket to notice a real human arriving, and a cron process that connects, posts and exits produces a member list that flickers.

tools/ambient/ ├── communities/ # ← the whole content surface │ ├── futebol.yaml # one file = one community + its cast │ ├── games.yaml │ └── … ├── src/ │ ├── schedule.js pure ← activity windows, jitter, rate caps, casting │ ├── scene.js pure ← prompt building, transcript splitting, typing timings │ ├── guardrails.js pure ← banned topics, advice, off-platform, identity, repetition │ ├── config.js ← load + validate a community file (fails at boot) │ ├── memory.js ← per-community JSON: recent topics, recent lines │ ├── generate.js ← ONE Claude call per scene, or a fixture │ ├── pqp-client.js ← real HTTP + /ws client │ ├── log.js ← JSONL audit log + kill switch │ └── runner.js ← the only file that touches network / clock / disk └── state/<community>.json ← memory, gitignored

The split is the maintainability claim. Every decision the system makes is computed by a pure function with the clock and the randomness injected, which is why "does the server go quiet at 3am" and "does a persona ever exceed its hourly cap" are unit tests rather than overnight observations. runner.js owns I/O and ordering and nothing else.

Personas as data

A persona is ~18 lines of YAML and appears nowhere in code. Adding one to a community is a diff to one file; adding a community is a new file plus a line in the shard config.

- id: cacau
  displayName: Cacau Ribeiro
  avatarSeed: cacau-ribeiro
  register: >                       # how they WRITE, not who they are
    Escreve em minúsculas, frases curtas, muita gíria de arquibancada.
    Usa "mano" e "cara". Raramente usa emoji, no máximo um.
  interests: [Palmeiras, categorias de base, estatística de rodada]
  activity:                          # wall-clock in America/Sao_Paulo
    weekday: ["07:15-08:40", "12:10-13:30", "19:30-23:15"]
    weekend: ["10:00-13:30", "16:00-23:45"]
  chattiness: 0.8                    # 0..1 — weights casting AND line count
  disclosure: character              # character | bot | undisclosed  (§04)
  replyToHumans:
    enabled: true
    maxPerHour: 4
    latencySeconds: [25, 210]        # a human does not answer in 400ms

register being about writing rather than biography is the single highest-leverage thing in the file. A model given "Cacau is a 28-year-old Palmeiras fan from Osasco" writes a character sketch; a model given "minúsculas, frases curtas, gíria de arquibancada, no máximo um emoji" writes chat.

The scheduler: curves, not a drip

Three mechanisms, all in schedule.js:

  1. Activity windows resolved through Intl.DateTimeFormat with a named zone, never a UTC offset. São Paulo dropped DST in 2019, but a community in a zone that has not would otherwise break twice a year, and the tests pin the case where a UTC day and a São Paulo day disagree.
  2. Triangular intensity inside each window — 0 at the edges, 1 in the middle. A boolean window produces five personas all appearing on the same minute at 19:30, which is the most obviously synthetic thing this system can do. The ramp makes evenings build and fade.
  3. Jitter everywhere. Scene cadence is inversely proportional to how awake the room is (busy evening ≈ every 7 minutes, dead Tuesday morning ≈ every 90), then jittered ±35%. The divisor is capped so no amount of activity turns the channel into a stream.

The conversation engine: one call per scene

The scheduler picks a server, a topic, 2–4 personas and a line count. One API call produces the entire exchange. This is the load-bearing cost decision and it is also a quality decision: a model that can see the reply it is setting up writes an actual conversation, while per-message calls produce five monologues that happen to be adjacent. §05 has the arithmetic — it is 3.3× cheaper and 5× fewer failure points.

The model's answer comes back as Nome: texto lines and is split by parseTranscript(). Two rules there matter:

  • A line attributed to somebody outside the cast is dropped, never reattributed. A model that invents a speaker has invented a member of a server that has a member list; posting that line under the wrong account is worse than posting one line fewer.
  • An over-length line is dropped, not truncated. A sentence cut mid-word is a tell; the scene reads fine one line shorter.

Delivery uses typingPlan(): typing time scales with message length (~22 chars/second, floored and capped), and the pause before a message is longer when the previous speaker was someone else — because you read before you reply. The typing indicator is re-sent every 2.5s inside the server's ~1/s sustained limit so "Cacau is typing…" actually stays on screen.

Humans outrank the schedule

In --watch mode every persona socket listens for message-broadcast from an author that is not part of the cast. A real human message jumps the queue: the runner waits a persona-configured 25–210 seconds, then runs a reply scene whose first line answers that person by name, capped at 3 lines.

The failure mode this cap exists for

A visitor says "oi" and six strangers answer within four seconds. That is worse than an empty server — it reads as a trap. Reply scenes are capped in three independent ways: shorter than ambient scenes, rate-capped per persona per hour, and de-duplicated so a backlog of human messages produces one reply, not one reply each.

Memory

One JSON file per community: the last 12 topics, the last 120 lines, and a coarse "who has talked to whom" counter. That is enough to answer the only question memory needs to answer at this size — have we already said this? — and the recent-topics list is fed back into the prompt as an explicit avoid-list and used to filter the topic pool before casting. §06 says what replaces it at 50 servers.

Guardrails

Every rule is stated twice: once in the prompt, once as a post-generation screen. The duplication is the point — a prompt is a request, and only one of the two still works when the model ignores it.

Observability and the kill switch

Every generated line is written to a JSONL log — posted, dropped by a guardrail, or dropped as a repeat — with the reason, the persona, the topic, the model, the token counts and the estimated cost. This is not telemetry. If anyone ever asks what did this account say and why, the answer has to be a file rather than a reconstruction.

AMBIENT_KILL_SWITCH=1 halts every write to pqp, read fresh on each call rather than once at boot so flipping it on a running machine takes effect at the next scene rather than the next release. It is the first gate in main(), before the runner touches pqp at all.

04The honesty question

The request was for accounts that do "real user things" in servers we advertise. Stated precisely, that is: present generated content as evidence of a user base, to people evaluating whether to join because of that user base. That framing is not hostile — it is just the framing a regulator, an app reviewer, or a journalist would use, and it is worth having the argument here rather than in public.

The three options

Option A

Undisclosed personas recommend against

What was asked for. Accounts that read as people, with nothing said anywhere.

The upside is real and I am not going to pretend otherwise. It is the only option where a visitor's first impression is unqualified — no badge to discount, no frame to process, just a room with people in it. Cold-start is the hardest problem a chat product has and this is the only version that fully solves it.

The exposure:

  • CDC art. 37 — publicidade enganosa covers any communication capable of inducing the consumer into error "a respeito da natureza, características, qualidade… do produto ou serviço". A populated user base is a characteristic of a chat service, arguably the characteristic. Art. 6º, III independently requires clear and adequate information about the service. This is not an exotic reading. not legal advice
  • App stores. Apple's Review Guideline 2.3 (accurate metadata / no misleading representations) and Google Play's Deceptive Behavior policy, which explicitly covers apps that misrepresent their content or functionality. A removal here is not a fine, it is the distribution channel.
  • Discoverability. The tell is arithmetic, not vibes: two accounts that post only within fixed windows, never at 04:00, never on a holiday, never with a typo they come back to fix. One curious user with a spreadsheet is all it takes, and the resulting screenshot is the only thing anyone remembers about the launch.
  • Irreversibility. Every other decision in this document can be changed next week. This one, once discovered, cannot.

The prototype supports it. disclosure: undisclosed, one word. I am telling you the word exists and telling you not to type it.

Option B

Soft disclosure safe, and a waste

A subtle bot badge, or one line in the server description.

Legally and policy-wise this is fine — a disclosed automated account is an ordinary product feature, and pqp already renders exactly this badge for webhook messages, so the UI exists.

The problem is that it buys safety by making the personas feel like spam. A [bot] badge on a person telling a joke about the Brasileirão is a category error: users have a strong prior that a badged account is a scoreboard or a moderation tool, and they discount it accordingly. You pay the full cost of building this system and get a room full of things nobody talks to.

Option C

Framed characters — o elenco da casa recommended

The personas are the server's fictional cast, and the server says so.

The frame is stated where a joining user sees it — in the server description, in each character's profile bio, and once in a pinned message — and then never mentioned again. Nothing else changes: the characters post, react, show typing, appear in the member list, and answer real people, because they are real accounts (§02, Option C).

Why this is not a compromise but the actually-better product:

  • Brazil already loved this. The Orkut research (communities-orkut.html §02) found that comunidades were identity performance — Bezerra & Araújo's vitrine pessoal, where you "dress an identity by bundling traits". Communities named Eu Odeio Acordar Cedo and Deus me disse: desce e arrasa! won millions of members on character and voice, not on population counts. A named cast with a consistent register is the same mechanic. The demographic that misses Orkut is exactly the demographic that reads a house cast as charm rather than as a trick.
  • It is a marketing asset instead of a liability. "Os personagens da casa" is something you can put in a press release. "We have 40 fake users" is something you spend the rest of the launch denying.
  • It survives contact with a journalist. Every other option has a bad-headline state. This one's worst case is a mildly charmed feature piece.
  • It removes the ugliest guardrail. Under A, a character asked "você é um bot?" has to deflect, and every deflection is a small lie that a screenshot makes permanent. Under C it can simply say yes.
  • The cold-start benefit is mostly retained. The thing a visitor needs is a room that is not silent and people who answer. A frame at the door costs a fraction of that and buys all of the above.
Recommendation, and how to make it reversible

Ship Option C. In the prototype, disclosure is a per-persona string with three values, validated at load — a typo throws rather than silently defaulting to undisclosed, because the one failure that must never happen quietly is the product's honesty posture changing by accident. character adds a profile bio and no name suffix; bot adds a visible [bot]; undisclosed says nothing anywhere. Nothing else in the runner branches on the value, so the policy is genuinely one line.

Two rules that come with C and are not optional: a character must never deny being a character when asked (the identity screen already blocks "não sou robô"), and a character must never DM a real user unprompted — a fictional stranger in a public room is a frame; a fictional stranger in your inbox is something else.

Why one call per scene, with the arithmetic

The naive design generates one message per call, and each call has to carry the transcript so far. Input grows across the scene: ~600, ~650, ~700, ~750, ~800 tokens for five lines — ~3,750 input tokens against 600, for identical output. That is $0.0046 per scene instead of $0.0014, and it buys worse dialogue, because no single call can see where the exchange is going.

Two things that do not help, checked

Prompt caching is useless here. Haiku 4.5's minimum cacheable prefix is 4,096 tokens; our system prompt is ~450. Nothing caches, at any volume. Do not design around it, and do not add tokens to a prompt to reach the threshold — that costs more than it saves.

Model tier is not the lever either. The same scene on Sonnet 5 is ~$0.0042 — 3× Haiku, and still only ~$75/month at 50 servers. If a community's voice is not landing, moving that community up a tier is affordable; AMBIENT_MODEL exists for exactly that.

065 servers → 50: what actually breaks

Not the money. Here is the honest list, in the order it will bite.

1. Repetition detection breaks first

Today: Jaccard over the last 120 lines, per community, blind to every other community. At 50 servers that fails three ways. A topic pool of six exhausts in a week and the avoid-list starts suppressing everything (the prototype already falls back to the full pool rather than going silent — the correct behaviour, and a symptom). A persona's voice starts repeating across communities even when its lines don't. And the O(n) scan per line becomes the runner's hot loop.

The fix, in order of when you need it: (a) generate topics rather than listing them — one cheap daily call per community turning a real-world prompt into 20 fresh topics; (b) move dedupe from token overlap to embeddings with a shared index across communities; (c) an automated weekly "voice audit" that samples 50 lines and flags any persona whose output has collapsed into a template.

2. Identity provisioning the argument for Option C

50 servers × 5 personas = 250 accounts. Under §02 Option B that is 250 Clerk MAUs, 250 sets of credentials, and 250 token refreshes to babysit. Under Option C it is a script and one table. This is the reason the identity decision should be made for the 50-server case now, even though launch needs 25.

3. The scheduler process sharding, not rewriting

250 WebSockets in one process is well within what the server holds (scripts/chat-load.mjs exists to prove that number), but one process is a single point of failure and a noisy neighbour. The runner is already stateless per community — memory is a file keyed by community.key, rate caps are in-process and per-community — so sharding is a config change, not a refactor: N systemd units or N Fly machines, each with a disjoint set of community files. Do not build a distributed scheduler.

4. Moderation and trust & safety newly load-bearing

250 accounts posting unattended in public servers is a real T&S surface. Under Option C they are ordinary users rows, so the existing sanctions machinery already applies to them — which is a feature: a character that misbehaves can be timed out by the same code path as anyone else. What is missing is the reverse direction: a character reacting to, quoting, or replying to a real user's harmful message amplifies it. At 50 servers, add a screen on the inbound message before a reply scene is planned, not just on the outbound lines.

5. Observability a digest, not a log

50 servers × 60 messages/day is ~3,000 generated lines a day; nobody reads that JSONL. Two additions: a per-community daily digest (scenes, messages posted, drops by reason, cost), and one alert — guardrail drop rate above ~15%, which is the earliest signal that a community's prompt has drifted or a model update has changed behaviour.

What keeps it maintainable: files, not code

The invariant to protect is that no persona and no community appears anywhere in src/. Adding a community is a YAML file plus a line in a shard's list. Changing a character's voice is editing three lines of register. Retiring one is deleting a block. If a future change requires a code edit to add a persona, that change is wrong.

Seed content strategy — the honest version

A server needs visible history to feel alive, and §01 established that the API cannot backdate it. So:

  1. Start the runner two weeks before launch. This is the recommendation. Two weeks × 60 messages/day ≈ 800 real, correctly-timestamped messages per server, with genuine gaps at 04:00 and genuine bursts on Sunday evening — which is more convincing than anything a backfill would produce, because it is the thing a backfill imitates. Cost for the whole pre-launch run: under $2.
  2. Seed the frame, not the history. On day one, write the server description, the channel topics, the pinned "quem é quem" post, and the character bios by hand. That is the content that makes a two-week-old server look intentional rather than empty.
  3. Backfill only if the calendar is lost, and treat it as a one-off SQL migration against production with a review, not as a runner mode. Timestamps must respect the same activity curves, or the fabrication is visible in a scroll.

Characters must not send DMs, and must not join voice. A fictional stranger in a public room is a frame; a fictional stranger in your inbox or your ear is something else, and no disclosure setting makes it comfortable. The runner has no code path for either, and it should stay that way.

What the prototype proved

  • Two dev-bypass accounts clear the age gate, take their persona display names, join a real server through a real invite, and appear as members.
  • A scheduled scene posts over the live WebSocket with human-shaped gaps (2.5–6.5 seconds between messages) and typing indicators held for the duration of each message.
  • A second persona reacts to a line it did not write, and the reaction is on the message when the channel is read back through the API.
  • Re-running against the same community suppresses the repeated scene: five of six lines dropped with reason=repetition, from memory alone.
  • AMBIENT_KILL_SWITCH=1 halts before the runner opens a single connection.
